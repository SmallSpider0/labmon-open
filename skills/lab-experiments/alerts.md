# 告警逐条怎么办

[SKILL.md](SKILL.md)「跑和盯」的展开说明。触发条件与背景见 labmon 仓库 [docs/workbench.md「告警」](../../docs/workbench.md#告警)。

收到 `labmon wait` 退出（退出码 1）后，**先按原命令重新挂上 wait，再逐条处理以下告警**。严禁通过 kill 运行中任务、修改任务名或更换 tag 来规避问题；通用处置原则是查明原因或上报 report。

## 看板页面上的改动

- `page:…`：维护者在看板修改了项目状态。
  - `move`（迁移登记）：将新清单登记到指定主机。
  - `rm` / `restore`：移除了登记或恢复了项目，若需要再跑才重新 `worker add`。
  - `pause`：等待恢复，不随意改动清单。
  - `config`：看板更新了 `monitor.toml`，wait 会自动拉取同步至本地，随项目提交即可，不得回滚。
- `sync_conflict:…`：本地与看板两端均修改了 `monitor.toml`。执行 `labmon project pull -c monitor.toml` 拉回看板配置（本地暂存至 `.labmon/monitor.toml.mine`），重新合并修改后 wait 会自动推送。
- `sync_error:…`：本地 `monitor.toml` 语法错误导致推送失败，按报错修复即可。

## 任务

- `failed:<任务>`：执行 `labmon status` 查看退出码、错误日志位置与日志末尾；若确认是 OOM 被杀（提示中含“同类下次估计抬高”），worker 已自动调整估计值，直接删除 `<状态目录>/<名称>.failed` 重排即可，无需手动修改 `vram=` 或更换 tag。
- `cpu_low:<来源>:<类>`：任务跑满分配核数但 GPU 利用率低（核给少了）。将清单中尚未开跑的同类任务调整为建议的 `cpus=`（不得超过单机配额），确保程序根据环境变量 `$LABMON_CPUS` 设定线程与 DataLoader 进程数。
- `cpu_high:<来源>:<类>`：清单声明的 `cpus=` 远大于实测峰值。运行满 3 次后 worker 会自动按实测记账，**无需修改清单**；若需立刻释放核配额可调小未开跑任务的 `cpus=`。
- `noprogress:<任务>:…`：运行超时且未输出进度行。通过 `labmon status` 确认日志与 CPU 是否活跃；仍在运行则切勿终止，给未开跑的脚本补齐 `PROGRESS k/N`。
- `log_silent:<任务>:…`：日志长期无更新。检查是否卡死；若属于阶段性静默，补齐进度行或在项目配置调大 `log_silent_min`。
- `void:…`：独占任务被打扰作废或被借用方挤掉，worker 已自动重新排队，无需手动删 `.failed`。

## 车道与队首

- `gpu_idle:<主机>:…`：检查车道是否有任务因暂停、依赖或缺少任务而空置。
- `lock_dead:<车道>:…`：worker 进程丢失（通常为容器重启）。执行 `labmon records --host <主机>` 核实，必要时请用户执行 `labmon worker start <主机>` 重新拉起。
- `cpu:<车道>`：队首因 CPU 核配额不足受阻满 10 分钟。若提示“记账比实测多”，等待系统自动回收实测值；若因主机配额不足，减小清单 `cpus=` 或更换主机，严禁改填 `cpus=0` 或绕过 labmon 直接起进程。
- `dep:<车道>:…`：依赖任务未就绪。若前置失败，修复后删除前置的 `.failed` 重跑；若依赖成环或名称写错，修正清单中的 `after=` 配置。
- 推演提示“排不上/推不出开始时间”：根据提示调整资源参数或更换可用主机，禁止干扰其他项目任务。

## 主机

- `ssh_fail:<主机>`：看板连不上该主机（超时约 2.5 分钟）。查 `labmon records` 是否处于重启或续租；切勿频繁执行裸 ssh 命令（避免触发限流）；若持续失联交由用户处理。
- `drain:<主机>:…`：主机处于排空状态，新任务不放行。等待续租或归还完成；若需紧急运行，将清单搬迁至其他正常主机。
- `disk_low:<主机>:<挂载点>`：磁盘余量偏低或独立主机触发 `disk_gate` 磁盘闸门（默认预警 `20 GiB`、停止线 `10 GiB` + `2 GiB` 滞回，触发后暂停放行新任务但不杀在跑任务）。
  1. 执行 `labmon disk` 查明占用来源与 14 天闲置可回收目录（严禁跑 du/find 遍历）；
  2. 先执行 `labmon worker clean <主机> [--project <id>]` 预览自管缓存（`.tmp/{cache,jobs}`），确认后加 `--yes` 清理；
  3. 若仍低于恢复线（停止线 + `2 GiB`）或接近软配额，向用户列出 `projects/` 下的大目录或可回收旧产物，经用户确认后手动清理；清理完成后闸门自动解除并恢复放行。
- `disk:<项目>`：共享盘近 24 小时增长过快。将中间缓存重定向到 `$LABMON_CACHE` 并声明 `needs=`，清理无用的临时 checkpoint。
- `bigwrite:<任务>:<时刻>`：单任务写共享盘超过 5 GiB。若写入的是中间特征或可重算数据，改为写入本地缓存。
- `idle:<主机>:<检查>`：GPU 持续空闲且保活检查未通过。检查是否有阻塞任务未放行；确认 worker 状态；清理 `monitor.toml` 中过时的主机检查。
- `throttle:<主机>:<起点>`：容器 CPU 持续被限流。检查程序内部是否写死了超额线程数，修改为遵循 `$LABMON_CPUS`。
- `returned_unfinished:<车道>:…`：主机已归还平台但队列尚未跑完。将清单重新登记（`worker add`）至其他可用主机。

## 借来的主机

- `borrow:<主机>:<时刻>`：借卡成功，可向该机登记新清单文件；同一清单登记即为搬走。
- `borrow_cut:<车道>:…`：到期前无法完成的任务，自动移出放行队列。根据建议将这些任务迁移至其他主机，或请用户在看板延长借用。
- `borrow_due:<主机>:…`：借用即将到期，停止向该机追加任何任务。
- `borrow_back:<主机>:…`：对方正在占用资源。暂缓提交新任务，根据用户决定是否提前归还。
- `borrow_done:<主机>:<时刻>`：借用已归还，将未完成任务迁移至自用主机。
- `pool_wait:<项目>:<车道>`：共有算力池中等待落机超过 2 小时。若带 `:nofit`（全池所有健康主机均放不下队首，立即触发）说明池内暂无满足硬件要求的卡，可调整资源需求或改挂至其他可用主机。
- `borrow_idle:<主机>:<起点>`：借用主机空置超过半小时。及时追加任务或告知用户提前归还。

## 临时主机（Colab 等）

- `ephemeral_down:<主机>:<实例>`：推模式临时主机超过 TTL 无心跳离线，看板已将残留 `running` 任务结转为 `failed`。按告警中给出的 `artifact_dir` 检查云盘 checkpoint 完整性，在新实例挂载 Google Drive 后以 `--resume` 续跑（细则见 [colab.md](colab.md)）。
- `ephemeral_dup:<项目>:<任务>`：同一项目有两台以上在线临时实例同时上报相同 `job_id` 为 `running`，存在互写覆盖云盘产物风险。立即核对各实例分工并停掉多余的重复实例。
- `ephemeral_disk_low:<主机>:<路径>`：临时主机上报的云盘剩余空间低于 1 GiB。用 `labmon disk` 查看临时主机存储区，及时清理旧 checkpoint 或中间产物，避免写盘失败。

## 挪法建议

- `rebalance:<项目>:<目标>:<原主机>/<清单>/<第一行>`：系统推演出更优调度方案。
  1. 通过 `labmon status` 核对最新推演建议；若建议已消失则不处理。
  2. 从原清单中剪除尚未开跑的任务行（若目标行有 `after=` 则插入其前）。
  3. 若建议为“在同一台上多开一条车道”：剪到该机一条新的长期清单并 `worker add` 登记；若建议为挪到指定目标清单（同机或跨机）：追加到目标清单末尾；若目标主机尚无相应环境清单，新建长期清单并配置 `QUEUE_STATE` 后执行 `worker add` 登记。
  4. 涉及跨机拷贝大文件时综合权衡耗时；若决定不采纳，向用户说明原因。
- `rebalance:<项目>:room:<主机>`：相关主机算力未吃满，运行 `fit --list` 并将排队任务分散至空闲主机。
- `rebalance:<项目>:est`：队首缺失时长估计导致无法推演，补齐 `est_min=`。
- `no_work:<起点>`：项目队列全部跑完，无待办任务。

## 看板自身

- `collector_stale`：看板采集停止，通知维护者检查服务。
- `skill_updated`：命令行已自动更新且随包 skill 同步变更。先重挂 wait，再重新阅读更新所涉及的章节。
- `server_unreachable`：连接看板持续失败 1 小时。通知用户并立即重新挂起 wait（客户端会自动退避重试，恢复后报 `server_back`）。
- `server_back`：看板连接恢复。重挂 wait 后通过 `labmon status` 与 `labmon check` 补看断网期间的状态。
- `wait_dup:…`：已有其他会话持有 wait 等待；若需本会话接管，使用 `--take` 参数启动。
- `wait_gone:…`：项目有待办任务但无会话挂起 wait，及时重新挂起监听。

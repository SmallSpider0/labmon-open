# 服务器端队列执行器（worker）

[`labmon/labmon_worker.py`](../labmon/labmon_worker.py) 放在服务器上跑，取代各项目自带的 `gpu_queue.sh`。每台主机一个 worker，
统一调度这台主机上登记的所有队列：准入、公平份额、独占、临时指令、保活。单文件，只用 Python 3.8 标准库，不 import 本包。
设计与依据见 [scheduler.md](scheduler.md)；工作台怎么显示它见 [workbench.md](workbench.md)。

## 命令

经 `labmon worker …` 操作：命令行发到看板服务（`POST /api/worker/<动作>`，#162），看板那边经 [`labmon/workerctl.py`](../labmon/workerctl.py) 每条命令一次 ssh（复用看板的连接）；
`start`、`stop`、`limit` 要管理员的 `admin` 令牌（`labmon login --admin`；`start` 只在内网入口），实验会话的 `project` 令牌做不了（[api.md「命令行」](api.md#命令行162)）：

```bash
labmon worker start 29                                   # 部署 main 上已提交的版本（工作区没提交的、分支上没合并的都不带）并拉起；已在跑则无缝替换（任务不受影响）；3 秒后不在就报失败（退出码 3，附 worker.log 末尾）
labmon worker add 29 /root/data1/alice/proj jobs/a6000.txt --project proj [--gpus 0,1] [--stop term]
                                                          # 登记一条队列：ROOT 是服务器上的绝对路径，JOBS 相对 ROOT；
                                                          # --project 必写（不写报错退出），是 monitor.toml 的 id：暂停、优先、借卡的
                                                          # “只给谁用”、作废的唤醒都按它认，看板不按目录猜；--gpus 限定只用某些卡
labmon worker add pool /root/data1/alice/proj jobs/p.txt --project proj    # 交给算力池（成员才能交；不许 --gpus、--stop boundary、gang=、占位任务），见 fleet.md「算力池」
labmon worker limit 29 heavy=2                           # 同 tag 同时运行数的上限（heavy= 删掉）：整台主机共用，各项目同名的 tag 合并计数
labmon worker status 29                                  # 这台的 CPU 配额与已记的核、登记的队列（清单跑空的标“空着”）、运行中（各记几核）与等待中的任务（等待行带排第几、是不是屏障、预计开始）；末尾一句与哪几台共用 worker 目录（看板按主机清单补）
labmon worker fit 29 x4_s110_seed2 [--project a1]        # 开并行车道前：与真放行同一份准入放不放得下，同卡并行时同类约要多久、卡吃不满是不是 CPU 受限（见“资源估计”）
labmon worker fit 29 ROOT JOBS --list --project a1      # 这条清单还会跑的行此刻能在共用 worker 目录的几台上再开几条车道
labmon worker rm 29 /root/data1/alice/proj jobs/a6000.txt  # 按清单文件认登记：ROOT 与 JOBS 拼起来是同一个文件就算（status 列的 ROOT/JOBS 从哪里断开都行，目录已删也撤得掉），只删这一条；已归还的主机经与它共用 worker_home 的在用主机代办（不连已归还的那台）
labmon worker stop 29                                    # 停 worker；运行中的任务继续跑，下次启动时接管
```

临时指令（`labmon pause` 等）与单元申请见下文各节。

## 装在哪、写什么

worker 装在主机的 `worker_home`（缺省 `<data_root>/labmon`，`data_root` 缺省 `/root/data1/alice`；共享盘上一份各主机共用，主机清单里可改）。
登记、状态和日志在 `hosts/<主机>/` 下：

| 文件 | 内容 |
|---|---|
| `queues/<目录哈希>.json` | 队列登记（目录、清单、项目、停法、限定的卡）；不许两条共用状态目录 |
| `status.json` | 每轮写的状态：主机容量、GPU 进程归属、运行中 / 等待中 / 旧 `gpu_queue.sh` 的任务、各队列、推演 `plan`、还会跑的任务 `todo`（见[依赖](#依赖)）、公平份额 `share`、本地依赖 `local`、存储、临时指令。看板探针读它；字段是看板 ↔ worker 的契约（`tests/test_contract.py`） |
| `usage.jsonl` | 每个任务结束一行（见“用量”） |
| `gang.json` | 本机成组的成员此刻怎样（等着、已留好、在跑）与近一天的结果；同组在别的主机上的 worker 读它（见[成组](#成组)）。没有成组的行时不建 |
| `press.jsonl` | 主机的 CPU 与读写压力每 5 分钟一行，留 14 天（见“用量”）；共享盘延迟的基线按它算，在共享盘上，容器重启不丢 |
| `events.jsonl` | 结构化事件（见“事件”） |
| `worker.log` | 文字日志（主机页的「worker 日志」）；出错崩掉时出错位置在这里 |
| `overrides.json` | 临时指令；`overrides.json.lock`、`events.jsonl.lock` 是读改写的文件锁 |
| `limits.json` | tag 上限（`labmon worker limit`） |
| `eta.json`、`sched.json`、`returned.json` | 看板写来的：运行中任务按进度算的预计结束；调度设置（主机清单的 `[sched]`，加上各项目算在谁名下的 `owner`）；主机清单里已归还的主机（`offers` 不让它们挡） |
| `stopped` | `labmon worker stop` 的标记：看板见到它不自动拉起 |

容器本地盘上 labmon 管的目录是 `/tmp/labmon/`：单格临时目录、项目缓存、单元申请的交换文件（见下）。

## 清单与状态

沿用 `gpu_queue` 的约定，看板不用改：

- 清单每行 `名称|命令`，`#` 开头是注释；每启动一个任务前重读，插队、追加就改清单（整体替换文件，写临时文件再 `mv`）。
- 同名 `.env` 在 ROOT 下用 bash 读入，读入时 `set -a`，赋值即导出（`PY=…` 不必再写 `export`）。worker 另外导出 `QUEUE_ROOT`、`PYTHONUNBUFFERED=1`，并清掉 `PYTHONPATH`（需要就在 `.env` 里设）。
- 状态目录（`.env` 的 `QUEUE_STATE`）里有 `lock`、`current`（`名称 PID 开始日期 开始时刻 放行的主机`；旧 `gpu_queue.sh` 与 11-10 前的 worker 不写主机）、`<名称>.done` / `.failed` / `.rc`、`queue.log`；`paused` 存在时不启动新任务。日志目录是 `QUEUE_LOGS`。
- 同一条清单登记在两台时（借来的主机还了再借回、自用主机恢复时旧登记还在，#88），`current` 是别的主机放行的、看板又没说那台已归还，这台一概不动它（`run_elsewhere`）：不接管、不收尾、不放行这条清单，
  等那台的 worker 自己收尾；那台 worker 不在也一样（判断不了就不动），等待原因写明、状态里等待项带 `elsewhere`（`[主机, 任务]`），事件记一条。那台已不在、任务确定没了时删掉 `current`，这台下一轮接着跑。
  旧格式的 `current`（没写主机）按别的主机状态里的 `running` 认。看板标成已归还的主机上放的，照旧当容器没了：有 `.rc` 的按它记账，没有的记中断、重排。
  开跑前再看一次 `current`，已有（别的主机刚放了）就这次不放。
- **一条清单只归一台**（#95）：`worker add` 把同一 worker_home 下别的主机（含已归还的、主机清单里已没有的）上同一条清单的登记搬过来，两边的事件里各记一条；
  原主机手上正在跑的照样跑完、由它自己收尾（它的 worker 重启了也照样接管，`adopt_left`；`run --replace` 升级时按旧 worker 退出前最后一轮写下的状态找），这台按 `current` 等它跑完再接着放，输出里写明。
  只删比这次登记旧的（按共享盘上登记文件的修改时间，各台同一个时钟）：别处刚登记了更晚的，这次让给那边、退出码 2，两个会话同时登记到两台不会互相删光。
  共用状态目录的检查也跨主机：别的主机上另一条清单用着同一个状态目录同样拒绝。查、写、比、删整段在共享盘上同一把锁里（`<worker_home>/hosts/registry.lock`），两个会话同时登记不会按过期的比较互删；
  worker 开跑一个任务时，从核登记还在、没有 `current` 到写下 `current` 也在这把锁里，搬登记插不到中间，新主机看得到原主机刚放的那个。
  搬来以后原主机还在跑的那个任务，项目页照样显示在跑、有进度：看板探针认 `current` 里放行的主机，不是这台的不查 PID（那是别的容器的），按在跑算。
  两台都登记着（旧版留下的）时，较旧的那台在较新的那台在用（worker 在、没 stop 过）期间不碰这条清单，状态里也不列，事件记一次；要在这台跑就再 `worker add` 一次。
  开跑前再核一次登记文件还在，这一轮刚被搬走的不放。`--pool`（看板的算力池搬清单时带，#79）在登记里记 `pool: 1`：看板据此认哪些是池放的（入池的自用主机上与主人的清单分开），状态的 `queues[]`、`todo[]` 带上它，`offers` 不叫会话挪这些清单；会话自己再 `worker add` 同一条清单就没有它了。看板上的「换到其他主机」就是逐条在目标主机上 `worker add`（[workbench.md「搬、移除队列登记」](workbench.md#搬移除队列登记)）。
- 任务在自己的会话里运行，退出码写进 `<名称>.rc`。完成留 `.done`；失败或被终止（退出码 130 / 137 / 143）留 `.failed` 并跳过，修好后删 `.failed` 即重跑。
- 日志 `<名称>.log` 追加写，每次开跑先写一行 `===== 时刻 labmon 开始（GPU …）=====`。看板的最后一行与进度、状态里的日志末尾、OOM 判断（`oom_of`）都只看最后一行分隔之后的（这一次的；`START_RE`）。
  这一次里逐字出现过的行算套话（库每次加载模型都打印的提示之类）：最后一行跳过它们，日志末尾把连着的折成一行「…（N 行与前面重复，略）」，OOM 判断看原文；数字在变的行（进度、loss）每行都不一样，不受影响。不按任务、不按关键词配置。
- 用 `CUDA_VISIBLE_DEVICES=<UUID>` 固定到选中的卡，`queue.log` 的“开始”行记下卡号和 UUID。各队列内部一次一个任务，不同队列（以及单元申请）在余量够时并行。

### 进度行

每个清单任务都要在日志里打进度行（占位任务除外），这是清单约定的一部分，不是可选项：

- 格式：一行里含 `PROGRESS k/N`（k 已做的步数，N 总步数，N > 0），后面可接标签与指标，如 `PROGRESS 120/196 [审计] loss=0.31`。看板按正则 `PROGRESS (\d+)/(\d+)` 认（项目的 `monitor.toml` 可用 `progress_re` 改，见 README），取这一次输出里最后一个进度行。
- 频率：至少每个 epoch 或阶段一行；一个阶段要跑十分钟以上的，在阶段里每几分钟打一行。看板 10 分钟以上（且超过平常间隔的 3 倍）没见到新进度，就当这一段不打进度、改按预计时长估结束。
- 输出：打到 stdout 或 stderr（日志就是它们），打完 flush。worker 已导出 `PYTHONUNBUFFERED=1`，Python 的 `print` 不用另加；别的语言、自己开文件写日志的要自己 flush，写进别的文件的看板看不到。
- 只看这一次的（分隔行之后的），而且只读日志末尾 32 KB：两个进度行之间别打大量别的输出，不然进度行会滚出这一段读不到。
- 多阶段任务打一个贯穿全程、只增不减的计数（各阶段步数相加为 N，标签写阶段名），不要每阶段从 1 重新数；各段各自从头数时看板把回退或总步数变化当换段，只按当前这段估速度。

看板拿它算速度与预计结束（[workbench.md「估时与 ETA」](workbench.md#估时与-eta)），预计结束写进 `eta.json` 传回 worker，推演按它排同机后面的任务。没有进度行，运行中的任务只能按预计时长减已用来猜，超了估时就看不出是慢还是卡住：超了预计、已跑满 30 分钟还一直没有进度行的，看板报 `noprogress:`（[workbench.md「告警」](workbench.md#告警)）。

### 资源提示

行尾可写 `gpus=N`（缺省 1，0 表示不用 GPU）、`vram=X`（每张卡的显存 GiB）、`ram=X`（内存 GiB）、`tag=heavy`、`exclusive=gpu|host`、`est_min=N`、`needs=…`，
以及依赖 `after=…`、`afterany=…`（见[依赖](#依赖)）、成组 `gang=组名:人数`（见[成组](#成组)）。
`cpus=N`（要几个核）进 CPU 记账（见[准入](#准入)）：没有同类历史、又确知要多核时才写；`io=heavy|light`（读写重不重）只记录、页面上显示，准入与推演都不看。
开跑时导出的 `LABMON_CPUS` 是开跑时给这个任务记账的核数（之后 CPU 记账按近 10 分钟窗口核数回收，它不变；见“用量”）；没设的 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 缺省同它。
建议写在行尾 ` #` 之后，不然这段文字会原样当参数传给程序；提示键前面不能是 `-` 或字母数字，命令自己的 `--gpus=0`、`--ram=64` 不算提示（`needs=`、`after=`、`afterany=`、`gang=` 只认 `#` 之后的）。
`vram=`、`ram=` 只被同 tag、同名的实测盖过，同一条清单里别的任务的历史不盖过它们（见“资源估计”）。

**占位任务**（等某个条件再放行的 hold / pause）按名字里的词认：`hold` 或 `pause` 在名字开头、结尾，或被 `_ . -` 或数字隔开——`hold`、`hold_x`、`x_hold2`、`pause-1` 算，`threshold`、`household`、`unpaused` 不算（worker 的 `is_hold`，看板的 `config.HOLD_RE` 是同一条规则，项目不能另配）。
占位任务一律不要卡、不独占，清单里写不写 `gpus=0` 都一样；它不受屏障限制，也不为它停保活。它守暂停、drain 这类临时指令，但续租、约定归还的截止不挡它：它不占资源，续租、归还打断了也只是重开后接着等。
它不占算力，`pause --now` 不停它；放行它的正规办法是满足它等的条件（命令是项目自己写的）。条件不会再来了，就先满足条件（建或删它等的标记）让它退出，再从清单里删掉这一行；不要 kill，会记成失败。
等别的任务跑完不要用占位任务，直接在那个任务上写依赖（[依赖](#依赖)）；占位任务只留给 labmon 看不到的条件（外部数据到位、人工确认）。
也不要在 GPU 任务的命令里先等条件再跑（如 `bash wait.sh && python …`）：等的那段时间它照样占着卡、记着份额，别的项目放不进来。等的部分拆成占位任务或 `gpus=0` 的任务，GPU 任务写 `after=` 它。
它的时长没法从历史推：就按 `est_min`（不看同类、不折算）；写了依赖的占位任务（以前的写法）在依赖满足后才开始，开始即放行。

### 依赖

“A 跑完再跑 B”直接写在 B 的行尾（同 Slurm 的 `--dependency=afterok / afterany`）：

```
train_s42|python train.py --seed 42        # est_min=300
eval_s42|python eval.py --seed 42          # gpus=1 est_min=30 after=train_s42
plot_all|python plot.py                    # gpus=0 est_min=5 after=eval_s42,eval_s43 afterany=exampleb/probe_x
```

- `after=a,b`：a、b 都跑成功才放行；`afterany=c`：c 跑完就行（成败都算）。可写几次，逗号分隔。
- 每一项按 `项目/任务名` 认，不带前缀的是本项目；被等的任务可以在别的清单、别的主机上（各主机的用量记录与 `status.json` 都在共享盘）。
- 每台 worker 每轮把自己所有登记清单里还会跑的任务写进状态的 `todo`（`list_state`：每条清单一项，带目录与清单路径，在跑的在前、其余按清单顺序，带写了的依赖与清单暂停的种类；在跑、在等的单元各一项；
  “还会跑的行”由 `rows_left` 一处算，推演也用它），
  别的主机按它认谁还会跑：排在时长不明的任务后面的、所在清单被暂停、drain 或截止挡住的都看得到。
- 被等的状态（`dep_state`），依次：
  1. 还会跑的（本机清单里没标完的、在跑的，别的主机 `todo` 里的）盖过以前的结果：删了 `.failed` / `.done` 重跑的、挪到别的主机重跑的接着等。
     只有那台写状态之后才记下的用量记录（已跑完）盖过它。那台 worker 不在（状态没更新、又没 `worker stop` 过，如续租重启）时它的 `todo` 一天内照样算；`worker stop` 过的（含借用归还）不算。
  2. 本机清单里有这一行的按标记：`.done` 成功、`.failed` 失败（跑成功过、重跑失败了算失败；几条清单说法不一的看用量记录的最后一次）。
  3. 其余看各主机用量记录里的最后一次（作废、被挤掉重排的不算；几秒内就失败、没量到用量的也算）。
- 没满足时（`dep_block`）这条清单停在这一行，同被临时指令挡住：不排位、不算等待时间（满足后才开始算）、不为它停保活；后面的行不越过它。
  等待原因写“等 X 跑完（预计 …）”，X 眼下不会动的另写明（“X 所在清单暂停中”、“所在主机 drain 中”、“X 在某主机上，那台 worker 已 N 分钟没更新”）。
  等不来的三种：`after=` 等的跑失败了写“等的 X 跑失败了…”；哪里都找不到（名字写错、清单没登记）写“找不到等的 X…”，但要持续满 2 分钟（`DEP_MISS_S`）才这么报：
  两边清单同时加行时，被等的那台可能还没认出自己清单里的新行，这台读别的主机状态又是每分钟一次（`PEER_EVERY`），刚加的行会有几十秒哪里都找不到（#56）。
  时限内同样挡着（不排位、不算等待、不为它停保活），等待原因写“等 X（还没在哪台主机的清单里见到它…；2 分钟后仍没有就报找不到）”。等待项的 `dep` 为 `wait`，照常记 `wait` 事件，不记 `dep` 事件、不告警。
  起算时刻是 worker 第一次判它找不到的时刻，写进状态的 `dep_miss`；worker 升级、重启接管时从上一份状态找回（那份状态 3 分钟内写的才认，停久了从头计时），不会每次重启都重等 2 分钟；
  找到了、或没人再等它了就删掉。
  依赖成环写“依赖成环，谁也轮不到：B 等 A，A 排在 B 后面”（`dep_cycle`：清单顺序也算依赖，一行要等它前面的都跑完；等排在自己后面的、互相等的、等自己的都算，别的主机的清单按 `todo` 一起找）。
  这三种在状态的等待项里标 `dep`（`failed` / `missing` / `cycle`），记 `dep` 事件，看板与 `labmon wait` 告警，改好（重跑、改名、改清单顺序、删掉 `after=`）下一轮生效。
- 推演里这一行排在依赖都满足的时刻（被等的在本机推演里的取推演结果，多半排在它后面才推演到，推演跑两遍；在别的主机上的取那台 `plan`；已跑完的按已结束），
  等的有一个排不上、跑不成的，这条清单写 `stuck`。plan 里它带 `deps`，项目页时间线从被等的任务结束连一条线到它开始（平时只画跨车道、推不出来的，悬停看整条上下游，[workbench.md「项目看板」](workbench.md#项目看板pid)），`labmon worker ls` 列出“依赖 X：等 A、B 跑…，预计 … 开始”。
- 清单行随时可改（整体替换），worker 下一轮按此刻的清单行重读；已经在跑的不受影响。

### 成组

多卡、多机的分布式训练（DDP）的几个进程要一起开跑、一个没了其余的也跑不下去（#180）。每个成员各写一行，行尾写同一个 `gang=组名:人数`：

```
ddp_r0|torchrun --node_rank 0 … train.py     # gpus=4 est_min=600 gang=ddp_a:2
ddp_r1|torchrun --node_rank 1 … train.py     # gpus=4 est_min=600 gang=ddp_a:2
```

- 组按 `项目 + 组名` 认，人数必写。成员可以在不同的清单、不同的主机上（一台自用、一台借来的也行），**放在不同的清单里**：
  同一条清单里的两行有先后，后一行要等前一行跑完，两行又要一起开跑，就成环了（等待项标 `cycle`）。成员之间不要互写 `after=`。
  同一个组名同时没跑完的行只能有这么多；几组就写几个组名。占位任务不成组。
- 认组：每台把还会跑的成员写进状态的 `todo`（每条清单的 `gang` `{任务: [组名, 人数]}`），别的主机按它认（同[依赖](#依赖)）；
  人数写得不一样、没写人数、凑不齐、多了都不排：没写人数的马上报，其余的持续满 2 分钟（`DEP_MISS_S`，两边清单同时加行时那台还没认出）才报，
  等待项标 `dep`（`missing` / `cycle`，告警同依赖）。
- 此刻怎样：每台把本机的成员写进 `hosts/<主机>/gang.json`（`gang_publish`，每轮推演之后；字段见 [schema.md](schema.md#worker-的状态文件)）：
  `wait` 还没留好（带推演里它最早何时放得下 `eta`、在队首被挡着的原因 `why`）、`ready` 已留好资源、`run` 在跑（开跑时刻 `t0`），各带人数与自己的预计时长 `dur`；
  结束的（`done` / `fail` / `stop`，带 `t0`、`t1`）留一天，worker 重启时读回。同组的成员在别的主机上时，这台每轮直接读那台的 `gang.json`（固定路径，不到 1 KB）。
- 先留后跑：成员轮到、放得下时不开跑，先把选中的卡与记账留着（`gang_hold`，准入核心 `place` 外面的一层），等待原因写“成组 G：资源已留好，等同组的一起开跑（预计 …）”；
  留到组里预计能一起开跑的时刻（别的主机上的成员取它 `gang.json` 的 `eta`，本机别的成员取上一遍推演里它最早何时放得下），这之前跑得完的任务照样用这份资源（回填，同[独占](#独占)），
  不算卡在资源上、不成屏障，但同放行一样给它的项目记上预计的卡·时（留着就占着，同一轮里这个项目后面的请求随之往后排）。同组别的成员留的总扣、彼此不算回填（要同时占着）。这一轮没重新留的（让位给屏障、不再是队首）当轮放掉，不再挡屏障。回填用了这份资源的那一轮起成员就不算留好（`gang_recheck` 按放行后的快照再看一遍：放不下的放掉、写 `wait` 与推演里何时放得下），
  同伴不会见它“已留好”先开跑。组里有成员说不出何时能放行（那台 worker 不在、还没给出状态、推演里排不上）的不留，等待原因写明是谁。
  两组在两台主机上各留了一个成员、正挡着对方的另一个时，按 `(项目, 组名)` 排在后面的组让出，两台判法一样，不会互相卡死。
  组里预计 2 分钟（`GANG_SOON_S`）内就能一起开跑的才为它停保活。
- 一起开跑：本机的成员都留好了、别的主机上的成员都此刻就能（`ready` 是那台 1 分钟（`GANG_FRESH_S`）内写的，或 `run` 开跑不到 90 秒（`GANG_JOIN_S`））时，按留着的卡一起放行，
  开跑的记下同伴 `gang_with`（状态的 `running[]`，接管时找回）。先看到全员就绪的那台先跑，另一台见它开跑就跟上；主循环里留着资源时每 2 秒重读同伴的 `gang.json`，
  几台开跑一般相差几秒。labmon 只管一起放行，不传地址：rendezvous（`MASTER_ADDR`、共享盘上的 init 文件之类）由项目自己做，超时照样留着。
- 一起停（`gang_watch`，按同一次开跑认：同伴在跑的开跑时刻相差 90 秒内；结束的要晚于这边开跑时见过的它最近一次结束（`gang_last`，记在 `gang_with` 的第三项，比的是同一台的时刻）。停下重排后几秒内又一起开跑的，上一次的结束记录不算这一次的）：
  - 同伴失败（含被作废）：按这条清单登记的停法停下（`term` 发 SIGTERM，`file:` 写停止请求），记失败（`.failed`）；
    先开跑的同伴在这边跟上之前就失败了（`gang_lost`：它开跑时记下了这一员、这一员之后没跑过），这边没开跑的也记失败（`gang_doomed`：`.failed`、一行 0 分钟的用量行），清单接着往下走；
    失败的同伴已不在 `todo` 里，按近 3 分钟见过它在哪台（`gang_known`，写进 `gang.json` 的 `known`，worker 重启后读回）去读它的结果；
  - 同伴停下重排（暂停、被挤掉、容器重启中断、没跟上）或所在主机已归还：同样停下，重新排队，等下一次一起开跑；
  - 开跑满 3 分钟（`GANG_LATE_S`）同伴还没跟着开跑（它留的资源刚被占了、清单刚被暂停、worker 没了）：停下重排。
  - 成组的成员被作废（独占被打扰）不重排、记失败，同伴照上面跟着停、也记失败；停法是 `boundary` 的停不下，只记一条 `gang` 事件、等它自己跑完（跑成功照记完成）。
    所以成组的清单请登记 `--stop term`。跟着停下的记 `gang` 事件；重排的同作废、被挤掉一样写进状态的 `voided`（`how` 为 `gang`），`labmon wait` 收到“跟着成组的同伴停下”。
- 时长：截止（续租、约定归还）前的准入与回填按组里最长的成员算（本机的取估时，别的主机的取它 `gang.json` 的 `dur`；有一个不知道的同没估时）；运行中的预计结束按自己的。
- 推演里同一套规则（`simulate`）：成员放得下先留，本机的都留好、别的主机上的预计到点就一起开跑；本机成员还不知道何时放得下的推两遍（第二遍按第一遍里最早何时放得下）。
  同组还排不上（凑不齐、成环、别的主机上的成员说不出何时能放行）的那条清单写 `stuck`，同停在依赖上一样记 `stuck_dep`（[能接别处的任务](#能接别处的任务offers)不当它原处跑不了）。
  plan 里成员带 `gang`。负载均衡不挪成组的行。

### 本地目录与本地依赖

worker 启动任务时设 `LABMON_SCRATCH`（单格临时目录 `/tmp/labmon/jobs/<项目>/<任务>`，跑成功后删，失败的留着查）与
`LABMON_CACHE`（项目的本地缓存 `/tmp/labmon/cache/<项目>`，跨格用、能重算的中间文件），`.env` 里也能引用；单元申请同样设。续租、容器重启会清空它们。

行尾 `needs=a,b`（可用变量与通配符）声明这格要读的本地文件：放行前缺了、命令又不会自己补（对同一路径先 `[ -f … ] ||`）的不启动，挡在队首、看板告警“缺本地文件”。
写成 `needs=本地<共享盘主副本`（来源可以是目录，按文件名对应）的，本地缺了先从主副本拷（写 `.part` 再改名，记 `stage` 事件）；主副本还没有的，这格跑成功后拷上去（`publish` 事件）。worker 不删主副本。
worker 每 5 分钟看一次待跑任务（含正在跑的）`needs=` 声明的、此刻在本地盘上的文件，写进 `status.json` 的 `local`，分“拷贝”（有主副本）、“重算”、补不了三种；看板的预备续租与续租确认据此列出受影响的任务（见 [workbench.md「平台续租」](workbench.md#平台续租)）。
**本地盘开机以来的新写入**（#149，`LocalDisk`）：续租、关机、换人会重启容器，根盘上开机以来写的都会清空，不只 `/tmp/labmon`。
容器根盘是 overlay、带平台的配额时（`rootfs_info`：根盘的文件系统是 overlay，总量比宿主盘小一成以上（`/etc/hosts` 由宿主绑定挂进来，statvfs 它得到的是宿主盘）；
状态的 `info.rootfs.ok`），根盘已用就是开机以来写进上层的量（测得准）；否则测不准，只扫 `/tmp/labmon`。
扫法与共享盘扫描同一套（`Disk` 的子类，见 [fleet.md「共享盘」](fleet.md#共享盘)的“怎么扫”）：后台线程一次做一件、做完接着下一件，限速每秒 1000 次元数据操作（`LOCAL_IOPS`，容器本地盘，接连几件合起来算），
变了的一小时后再扫、没变的间隔翻倍，太慢的拆开，任务跑成功后它的单格临时所在的单位提前重扫，共享盘慢时同样推迟（`io_yield` 的键 `lscan`）；不要租约，每台扫自己的。
不同的只有：只进开机以后动过的目录（overlay 上开机后写过东西的目录都已复制到上层，ctime 晚于开机（PID 1 的启动时刻）；早于开机的整棵跳过，不跨文件系统，
`/proc`、`/sys`、`/dev`、`/run` 不进），只数 ctime 晚于起算时刻的文件；对账看 labmon 之外的新写入（根盘已用 − labmon 目录的占用）比上次变了 64 MiB（`LOCAL_DRIFT`），
变了把最近一天有写入的单位提前；索引在容器本地 `/tmp/labmon/disk.json`（续租即清）。labmon 自己的目录拆到 `cache/<项目>`、`jobs/<项目>` 一级，
同一次扫描给出各项目缓存与单格临时。结果写进状态的 `storage`（字段见 [schema.md「工作台的全局快照与接口」](schema.md#工作台的全局快照与接口)），
其中 `wrote` 是 labmon 之外新写的大头：前 8 处，四级及以下归到前三级 `/a/b/c`，一、二级目录本层的文件记成 `<目录>/.`（组内服务器的探针同一规则，见 [fleet.md「本地盘」](fleet.md#本地盘)）。
借来的主机上从借来时算起（guest 指令的时刻，同一次借用里取最早的那个），归还的确认据此列“借用期间我们写的”（归还只删 `/tmp/labmon`，这些留在对方那边）。
容器私有的 `/dev/shm`（挂载来源是 `shm`）的已用记在 `info.rootfs.shm`，续租同样清掉；与宿主共用的 tmpfs不算。
看板把这两样合成 `lw`（`fleet.local_writes`）：labmon 之外的加私有 `/dev/shm` 到 1 GiB（`LOCAL_ACK`），续租、关机、换人前要先勾确认（[fleet.md「本地盘」](fleet.md#本地盘)）。

### 独占

行尾写 `exclusive=gpu`（独占所用的卡）或 `exclusive=host`（独占整台主机），用于开销评估、计时测量。

- 轮到它时先把卡（主机）留住，上面的任务跑完、腾空后才启动；留着期间预计在腾空前跑得完的任务照样放（回填，腾空时刻 `hold_until` 取上面任务预计结束的最晚一个，有一个时长不明的就不回填）。它运行期间那张卡（主机）也不放别的任务。
- 只有真在排队、卡在等腾空的才留着卡：被临时指令（项目暂停、drain、截止）或依赖挡住了，或因为别的原因放不了（缺文件、放不下、截止前跑不完、tag 到上限、在拷本地依赖、内存闸门），留着的卡当轮放掉，别的项目照常用。
- 只为 labmon 的任务留卡。挡着的是 labmon 之外的进程（同卡的 GPU 进程；整机独占另看连着两轮占 1 核以上的 CPU）时只能等它们用完，这时不留卡（主机）、不算卡在资源上，别的任务照常放。借来的主机上对方回来用最容易碰到。
- 占位任务不参与；不用卡、几乎不占 CPU（不到 0.2 核）的常驻任务（如等单元放行的监督进程）不用等它跑完，也不算打扰。
- 运行中连着两轮（约 20 秒）同卡（整机独占：同机，或 labmon 之外的进程占了 1 核以上）有别的进程，结果就不能用了：不管停法直接 SIGTERM，记“作废”，清单任务重新排队，单元由申请方重新申请；看板经 `labmon wait` 报 `void:`。放行前与作废看同一个判定（`intruders`）。
- 借来时对方在轻用的，独占卡也扣给对方的预留（扣完放不下就不放），多卡时先挑没给对方留的卡。
- 用量记录写明运行期间同卡、同机有没有别的任务，计时结果据此核对是否真的独占。

### 借来的主机给对方留余量

借来的主机（[fleet.md「借用」](fleet.md#借用)）上 worker 收到 `guest` 指令：只给指令里的项目用（`worker add` 也拒绝别的项目），带着给对方留的量 `keep`（显存、内存、CPU；`hold` 为借来时对方在轻用）。

- 借来时对方在轻用的，放行时从对方的卡（单卡就是它；多卡是 0 号卡与对方有进程的卡）的可用显存、容器内存里扣掉对方还没用上的预留；CPU 扣 max(对方实测, 预留的核数)。借来时对方空着的不扣，对方回来用时有了这人 GPU 进程的卡就算超出。
- 对方另起、`ka.sh` 停不了的保活（见下文“卡上有对方另起的”那条）占的核不论预不预先留、在不在说好不用的时段里，都另从可用核数里扣（`other.ka_cpu`），不和预留取 max，也不看连着几轮。
  核数按各棵保活树（根的 PID 与启动时刻）分开记累计、各自求差：改类（漏读一轮 guest 指令后又读到）的那一轮不会把它启动以来的 CPU 一起算进来，一棵退出不丢别的几棵这一段的核数，新冒出来的树第一轮为 0；只看 `/proc` 的累计，不掺容器用量减任务（有测量误差、会为负）。它的内存本来就在收不回的 `anon` 里，可用内存的算法不变。
- 对方用量（labmon 之外的进程各卡显存；收不回的内存 `anon` 减去我们的任务与所有保活，不按工作集算；CPU 是容器用量减去我们的任务、worker 与所有保活）超出预留：超出的那张卡不放新任务，内存或 CPU 超出时整台不放，回到预留以内 10 分钟后恢复。CPU 连着两轮超出才算：刚停的保活那一段用掉的核没法扣（进程已不在），会算到对方头上，一轮的尖峰不挡放行。
  “所有保活”含 `ka.sh` 管的和对方另起、`ka.sh` 停不了的（#37）：保活只占位，不算对方干活；组内探针给对方算预留时按 `[fleet] keepalive` 的字样认保活、两种都扣，两边才同口径。
  差别：worker 只认命令行里的 `keep_alive`，探针认整个字样列表（页面上点“这是保活”会往里加）。现在列表里只有 `keep_alive`，两边一样；真加了别的字样又借那台时，再让 guest 指令带上字样下发。
  保活按整棵进程树算（GPU 上的保活进程与它的子孙，如 DataLoader 子进程）：内存扣各进程 PSS 之和，CPU 扣这一段里的核数（`ka_cores`）。只扣 GPU 进程本身会把子进程的内存与核数算到对方头上（#29：27-15152 上少扣约 0.6 GiB）。组内探针给对方算预留时内存按同一口径扣（[fleet.md「给对方留的量」](fleet.md#借用)），两边才比得了；探针的 CPU 只有 `ps` 的 %CPU（进程整个生命期的平均），与这里的“这一段”不同。
  保活这一轮没认出来（刚拉起还没建 CUDA 上下文、nvidia-smi 超时）时，上一轮认出的保活进程还在（PID 与启动时刻都对得上）就照样算保活（停不了的照样算停不了的）；CPU 按整棵树的累计求和求差（`cpu_since`，同任务的用量），新进树的保活连它启动以来的 CPU 一起扣（所有保活合起来那份，从对方用量里扣；停不了的另扣的那份见上，新树第一轮为 0），不会连着两轮判超出。
- 对方说好不用到某个时刻（`keep.away`，用户在借卡弹窗里勾的，取约定时间；Issue #30）：到那时以前不预先留（卡、容器内存、CPU 都不扣对方还没用上的部分，CPU 只扣对方实测），也不判对方的内存、CPU 超出（此刻占着的照算在可用量外；勾上前已有的超出这一轮起就不挡，不等 10 分钟）。CPU 连着几轮超出照样累计（`cpu_hot`），只是不判；作废那一轮起已连着两轮超出的立刻算超出。
  对方回来只认两件事，回来了就作废这次（`end_away`，记“借来的主机”事件），这一轮起按普通规则；状态 `guest.away = {until, end, why}`，看板据 `end` 清掉、提醒。到点后同样按普通规则。
  - 新的对方 GPU 进程：说好不用开始时（worker 第一轮看到 `away` 时；重启后以重启时为准）对方已有的 GPU 进程（轻用时开着的 Jupyter 之类）照算在可用量外，不算回来、不挡那张卡，变大了也不算（第一轮没读到 GPU 表就等读到了再取）；勾上前那张卡已记的超出同样这一轮起就不挡；之后新出现的，那张卡当轮就不放新任务，连着两轮都在才作废（归属只看一次采样会误判：任务刚结束 nvidia-smi 还列着、宿主 PID 对不上）。
    对方新起的 `ka.sh` 停不了的保活（如对方的看门狗拉起了脚本不同的保活）不算回来、不作废，只是那张卡不放（保活只占位、不算对方干活；维护者 11-09 定，#37）；同一张卡上另有新的对方进程照样算回来。到点、作废或指令不带 `away` 后基线清掉，再勾（约定时间相同也一样）重新取、从头计。
  - 内核杀了 labmon 之外的进程（`owner_oom`，什么时候算见下面通用的那条）。
- 卡上有对方另起的、`ka.sh` 停不了的保活（见「保活」）：在预留以内也算那张卡超出，原因里写明要对方停。它不算对方的内存与 CPU（见上），只挡它所在的那张卡，别的卡照放（#37；以前算成对方的用量，多卡时会让内存或 CPU 超出预留、整台不放）。
- 快撞上限：对方超出预留、且那张卡空闲显存不到 1 GiB，或容器里收不回的内存到上限的 95%。不停正在跑的（这一格跑完，停了白跑），状态里记 `guest.tight`，看板提醒用户线下和对方商量，要停就点「现在停」。
- 算力池借来的（guest 指令的 `keep.pool`，[fleet.md「自动借、放、还」](fleet.md#自动借放还25)）：对方超出预留的几项里，去掉只因 `ka.sh` 停不了的保活超出的卡（该卡上对方的 GPU 进程全是这种保活），再加上有了对方 GPU 进程（停不了的保活除外）的卡（预留以内也算：池借只在 GPU 空着时借），写进状态的 `guest.owner`，算主人回来了；
  有它时整台不放（`guest_block`），看板同一轮要还。`offers` 为空：池里的清单放到哪台由看板定，不给挪法建议。
- 我们的任务 `oom_score_adj` 设 1000（清单任务的外壳与单元 exec 前），真撞上容器内存上限时内核先杀我们的。
- 被挤掉（只看借来的主机上失败的清单任务，判定同[用量](#用量)里的 OOM：`oom_of`）：容器内存 OOM 被杀；或 CUDA OOM 且对方在它的卡上用过显存。是就不记失败、重新排队，同一任务最多两次，经 `void:` 报；不记 `oom`，不抬同类的估计。
- `oom_kill` 涨了又不是我们的任务被杀：记内核杀了 labmon 之外的进程（`owner_oom` 事件），看板据此提醒、调高预留，说好不用的这次作废。
  上一轮还有我们的任务进程、或有任务在跑时不算：我们的任务 `oom_score_adj` 是 1000，有它们在内核一定先杀我们的；DataLoader 子进程或某个 rank 被杀、
  任务以退出码 1 退出或接着跑时 `squeezed_by` 认不出，这时只记一条“借来的主机”事件，不算对方的。

## 用量

worker 每轮现读主机容量（各卡显存与利用率、cgroup 内存上限、工作集与收不回的内存 `anon`（用量 − 文件页，含 shmem，不算页缓存，见[准入](#准入)）、CPU 配额、磁盘、容器启动时间），并记每个任务的内存（会话内进程 PSS 之和）、核数与显存
（nvidia-smi 给宿主机 PID，经 `/proc/<pid>/sched` 对回容器 PID；3.10 内核可行），写进 `status.json`（运行中任务的开始时刻 `t0`，epoch 秒）。
对不上的计算进程记为“labmon 之外”。旧 `gpu_queue.sh` 正在跑的任务也统计（`external`，开始时刻 `t0` 从状态目录的 `current` 换算）。

任务结束时写一行到 `usage.jsonl`：起止 `t0` / `t1`（epoch 秒）、项目、峰值显存与内存、平均核数、运行期间所用卡的平均利用率（`gpu_util`）、时长、退出码、估时、GPU 型号、
占的卡数 `cards`、放行前等了多久 `wait`、是不是停下重排的（`requeued`）、失败是不是 OOM（`oom`，见下），以及同卡、同机还有谁；CPU 与读写见下。各主机的都在共享盘上，worker 一起读（`load_hist`，文件变了才重读）：借来的主机一上来就有同类记录。供资源估计、预计时长、`fit` 与公平份额用。

清单任务失败（不是停下、作废的）时认一下是不是 OOM（`oom_of`，#62）：这一次的日志末尾 40 行是 CUDA OOM 记 `oom: "vram"`；运行期间容器的 `oom_kill` 计数涨了
（cgroup v1 没有这个计数时看 `memory.failcnt`）、且退出码 137 或没留退出码，记 `oom: "ram"`；都不是为 `null`（11-10 前的行没有这个字段，当作不是）。
借来的主机上被对方挤掉的（容器 OOM 被杀；CUDA OOM 且对方在同卡）照旧重排（`squeezed_by` 用同一个判定），不记 `oom`，挤满次数后记失败的也不记。
记了 `oom` 的，失败事件与队列日志句尾写“CUDA 显存不够（OOM）/ 容器内存撞上限被杀（OOM），同类下次估计抬高”（见[准入](#准入)的资源估计）。
子进程被杀、主进程以退出码 1 退出的（DataLoader worker 被杀）认不出；单元申请没有日志、不知道退出码，不认。

### CPU 与读写

都是读本机 `/proc` 与 cgroup 的累计计数、两轮求差，沿用 10 秒一轮的采样，不另起线程、不遍历目录（Issue #5 期 1 量，#6 期 2 用）。
任务的 CPU 峰值进 CPU 记账的估计（见[准入](#准入)）；共享盘慢时扫描与拷本地依赖让路、另记“读写拥塞嫌疑”（见下）；读写的量与 `io=` 准入不看。

- **每个任务**（`measure`）：会话里各进程 `/proc/<pid>/io` 的 `rchar`、`wchar` 加起来（read / write 系统调用的量，共享盘与命中页缓存的都算；子进程被回收时内核把计数并进父进程，求和不重不漏），
  核数同以前。运行中任务的 `use` 带此刻的 `rd`、`wr`（MiB/s）、累计 `rd_b`、`wr_b`（字节），以及按 60 秒窗口算的峰值 `cores_peak`、`rd_peak`、`wr_peak`；
  任务结束时这五项与清单的 `cpus`、`io` 写进用量行。worker 重启接管任务时从旧状态的 `use` 找回上一轮的计数，累计读写与峰值窗口接着算；只有从期 1 之前的 worker 升级上来的那一次（旧 `use` 里没有计数）从接管时算起。合计变小的那一轮（回收者不在进程树里）按 0 算。
- **主机**（`Worker.press`，状态的 `info.press`，“此刻”取近 1 分钟的差值）：
  - `thr`：CPU 被配额限流的周期占比（%，cgroup `cpu.stat` 的 `nr_throttled ÷ nr_periods`）；
  - `nfs`：共享盘（`/proc/self/mountstats` 里 `data_root` 所在的 NFS 挂载）READ、WRITE 每次的平均执行时间 `ms`（含客户端排队；这段没有读写为 null）、每秒次数 `ops`、`mib`（MiB/s），
    客户端地址 `addr`（同一物理机的几个容器相同），基线 `base`、样本数 `n`、此刻慢不慢 `slow`（见下）。计数是宿主机挂载的，同一物理机的几个容器共用一份；
  - `disk`：本地盘（`/tmp` 背后的块设备：cgroup blkio / `io.stat` 里本容器读写最多的那块，读不到用 mountinfo 的设备号；`local_dev`）在 `/proc/diskstats` 里的忙碌占比 `busy`（%）与每次平均用时 `await`（ms）；
  - `psi`：有 `/proc/pressure` 时（4.20 以上的内核；29 是 3.10，没有）各项的 `some avg60`。
  计数变小（容器重启后 cgroup 归零、换了设备）的那一项那一轮为 null；worker 刚启动的第一轮都为 null。
- **CPU 限流**（#39，状态的 `throttle`）：`thr` ≥ 25%（`THR_HOT`）起算一段限流，降到 10%（`THR_COOL`）以下才算结束（`thr_step`，滞回免得在门槛上来回跳；`thr` 为 null 的那一轮沿用）。
  限流中状态写 `throttle`：`{since 起点, for 已持续秒数, thr, alert 持续满 10 分钟（THR_HOLD_S）, over 超核的任务, other labmon 之外此刻占的核（不含保活，含旧 `gpu_queue.sh` 的任务）}`，其余时候为 null；
  超核（`cpu_over`）：最近一个 1 分钟窗口的核数（`use.pks`，没有或过了两分钟取每轮的 `cores`）≥ 开跑时导出的 `LABMON_CPUS` × 1.5、且多出至少 1 核，占位任务不算。
  起点写在状态里，升级、重启时 `load_prev` 找回（状态没过期时），告警不从头计时。准入与推演不看它；看板按 `alert` 告警（[workbench.md「告警」](workbench.md#告警)），门槛只在 worker。`labmon worker status` 也列一行。
- **基线历史**：每 5 分钟往 `press.jsonl` 记一行这 5 分钟的聚合值 `{t, ms, ops, mib, busy, await, thr}`，留 14 天（`append_jsonl` 按保留期修剪），worker 重启时读回。
  共享盘慢的基线 `io_base`：近 14 天每秒不少于 2 次读写（`IO_MIN_OPS`）的样本的 95 分位，且不低于 20 ms；样本不到 288 个（约一天）时取 20 ms。
  次数下限是为了把 worker 自己的小写排除在外：同一物理机 3 个容器的 worker 每 10 秒各写一次状态，合计不到 1 次/秒，几次小写的时间不代表盘慢不慢；真有任务在读写时次数远高于它（一个读者在 500 ms/次时仍有 2 次/秒）。
  **共享盘慢**（`nfs_slow`，状态里 `info.press.nfs.slow`）：此刻每次读写的时间超过基线，且每秒不少于 2 次。
  `press.jsonl` 写不进时只少这一行历史（基线照用内存里的），不影响这一轮的采样与准入，5 分钟后再试；连续失败只在 worker.log 记一次。
- **`LABMON_CPUS`**：开跑时导出（单元申请放行时经 `.ok` 带给客户端；旧 worker 的 `.ok` 不带时客户端按 `--cpus` 取，没写按 1 核），是开跑时给这个任务的核数（开跑满 10 分钟后记账会按实测回收，导出的值不变）：估计（`estimate` 的 `cpus`，见[准入](#准入)；按实测收小了记账的仍是清单的 `cpus=`，`cpu_threads`）封顶到这台的记账上限（`cpu_give`；历史是各主机一起看的，在 17 核的主机上量到的峰值到 7 核的主机上不能照给），至少 1（写了 `cpus=0` 的不记账，导出 1）。
  容器里 `nproc` 报的是宿主机的核数（29 上 144，配额只有 17），项目拿 `LABMON_CPUS` 设线程数、DataLoader 进程数。
  任务环境里没设（或为空）的 `OMP_NUM_THREADS`、`MKL_NUM_THREADS`、`OPENBLAS_NUM_THREADS` 缺省设成 `LABMON_CPUS`（`cpu_env`，#38；清单任务与单元都一样，`cpus=0` 的是 1）：
  不设时 BLAS、OpenMP 与 PyTorch 按 `nproc` 起线程，一个任务就能把配额用满、被限流。已设的不盖：worker 与单元申请方自己环境里的不动，
  清单的 `.env` 与清单行前缀（`OMP_NUM_THREADS=8 python …`、`export …;`）在补缺省之后才生效（`bash -c` 里先 source `.env` 再 eval 命令行），要更多线程的在这两处写一行。
  按 `LABMON_CPUS` 设并行数的任务（现在也包括没自己设线程数的 BLAS/OpenMP 任务），历史峰值只会照着给它的核数长（给 1 核就只开 1 个、量到的也是 1 核），所以第一次要写 `cpus=`；没写又没历史的按 1 核。
- **开跑核数给多给少**（`cpu_fit`，#46；状态里运行中任务的 `cpu_fit`）：开跑满 10 分钟（`cpu_warm`，接管的从接管起量）才判，给的核数是开跑时导出的 `LABMON_CPUS`。
  “给少了”（`low`）：近 10 分钟各 1 分钟窗口核数（`use.pks`）的平均不少于给的 × 0.9（`CPU_BOUND_FRAC`），且所用的卡里有近 10 分钟利用率低于 50%（`UTIL_LOW`）的：卡吃饱了加核也没用，不用卡的不判（单线程脚本本来就只用 1 核）。
  建议值 `sug` 是给的 2 倍，封顶到这一类每条最多能给的核（`cpu_budget`，#112）：labmon 全停时能给的（`cpu_room`，已扣 labmon 之外的、给对方的预留与停不了的保活）减去同机别的任务（别的项目的、本项目别的类的）已记的核，再按本项目同一类（`cpu_cls`）此刻同时在跑的条数均分、向下取整：
  同类几条车道照同一条建议改清单，加起来也不超过配额（配额 7 核、同类两条各给 2 核时建议 3，不是 4）。不比给的多（已给到配额、配额被别的任务与同类分完了）为 null；读不到配额的不封顶。
  给少了的另带 `room` `{per 每条最多几核, cap 记账上限, other 别的任务已记, out labmon 之外与预留占的, same 同类几条, kept 有没有给对方留}`（读不到配额为 null），看板写进告警。预算是判出那一刻的，跟着这次运行留到跑完。`fit` 的“先给它那条车道加核”就是它（只看 `how`，不看 `sug`）。
  “给多了”（`high`）：只认写了 `cpus=` 的（估计来自提示值；按历史估的会往实测靠，按实测收小了记账的已经让出，都不判），跑到现在的 1 分钟峰值 `cores_peak` 不超过给的一半（`CPU_SPARE_FRAC`）且少至少 1 核（`CPU_SPARE_MIN`）：看整段峰值，开头加载阶段用过的核不算多给。
  建议值按峰值 ×1.1 取整（`cpu_from_peak`，与 `estimate` 按历史估同一处）。写成 `{how, avg, peak, give, sug}`（给少了另有 `room`），都不是为 null；占位任务不判。同一次运行判出来就留到跑完（`Worker.cpu_hints`，接管时找回），测量在门槛两侧来回时不反复出现、消失；`fit` 要此刻的样子，照旧现算。只做提示：准入与记账不看它（同类一直给多了的由 `estimate` 收小记账，见[准入](#准入)），看板据此出只给实验会话的 `cpu_low:`、`cpu_high:`（[workbench.md「告警」](workbench.md#告警)）；写进状态时补上类 `cls`（tag，没有 tag 取去掉种子编号的名字）与 `by`（`tag`/`name`，`cpu_cls`），看板按它合并同类。
- **共享盘慢时让路**（`Worker.io_yield`）：共享盘慢时不开始新的共享盘扫描与本地盘扫描（`Disk.step`，共享盘的写在状态的 `disk.yield`），不起新的拷本地依赖的线程（等待原因写“共享盘慢…，推迟拷 N 个本地依赖”）；已经在做的不打断。
  同一件事连着推迟满 30 分钟（`IO_YIELD_MAX_S`）就照做一次、重新计时：一直慢时扫描每 30 分钟做一件，每个拷贝最多晚 30 分钟。开始推迟与推迟满照做时各记一行 worker.log。准入不看。
- **读写拥塞嫌疑**（`Worker.io_suspect`，事件 `io_suspect`）：在跑的非占位任务已跑过同类历史给的预计时长（`duration` 的 `same`；借来的比值、清单估时不算）的 1.5 倍（`SLOW_RATIO`），且此刻共享盘慢，记一条事件：已跑与同类时长、此刻 ms 与基线、每秒次数，以及同一物理机上在跑的别的任务。
  同一任务只记一次（运行中任务的 `io_sus`，写进状态、接管时找回）。只记录：不告警、不改准入与推演。同一物理机按共享盘的客户端地址 `addr` 认（29、29-15158、29-15159 相同）：`peers` 读别的主机状态时记下 addr 相同、没过期的那几台在跑的任务；
  ms 与次数只用本机读到的这一份，同一物理机几个容器读到的是同一份计数，不相加。

## 准入

每个请求（清单队首的任务，或一次单元申请）带资源提示；能不能放、选哪几张卡、独占留卡与回填、给对方的预留只有一份规则（`place`），输入是资源快照（`Worker.snapshot`）：真放行按实时采样拼，推演在模拟的时间轴上维护同样的快照。

- **资源估计**（`estimate`）：显存、内存逐项依次看（#61）：同 tag 的历史，否则去掉种子编号后同名的历史（近 5 次峰值的最大值 × 1.1，两项一起取自先找到的那一档）›
  清单写的提示值（`vram=`、`ram=`，大于 0 才算写了）› 同一条队列的历史（同样 × 1.1）› 0。同一份清单里可以是完全不同的任务，同队列是最弱的一档，不盖过明写的提示值：
  新 tag 的大任务追加进跑过小任务的清单，按它写的 `vram=` 估（以前按同队列估成小任务的峰值，一张卡同时放行好几个、OOM）。没写提示值的那一项照旧看同队列。
  来源分开记：显存 `src`、内存 `ram_src`（一项写了提示值、另一项没写时两者不同）；同时给出单跑（同卡没有别的任务）时的平均 GPU 利用率 `util`，跟着显存的来源走（显存用的是提示值或 OOM 下限时没有）。
  历史只认跑成功的、或跑了 5 分钟以上的，且不是 OOM 的（用量行的 `oom`，见[用量](#用量)）：OOM 那次的峰值是被当时可用的量截住的，比真实需要小。
  “近 5 次”按跑成功的数；跑了 5 分钟以上又失败的（不是 OOM）没跑完，峰值只是下限，只在比这 5 次里最旧那条新时参与取最大值，只能抬高、不占名额（`peak_rows`，#134：以前近 5 次都是这种失败时，估计掉到它们的小峰值）；一次也没跑成功的照旧取最近 5 条。CPU 的峰值核数同样这么取。
  **OOM 后抬高**（#62）：同 tag、同名两档里，各取这一档最近一次跑成功之后的 OOM 记录，给 OOM 的那一项（显存或内存）一个下限 max(那次放行时的估计 `est` × 2, 那次量到的峰值 × 1.1)，几条取大；
  这一项的估计取 max(上面按顺序取的值, 下限)，提示值写小了的同样抬高。来源写成“同 tag 上次 OOM：放行时估 7.1 GiB ×2”（峰值那头大时写“OOM 时峰值 14.9 GiB ×1.1”）。
  连续 OOM 连续翻倍（每条的 `est` 已含上一次的下限：7.1 → 14.2 → 28.4 → 整卡），按整卡、整个容器封顶（见下）；这一档有一次新的跑成功（退出码 0；跑了 5 分钟以上又被停下或别的错误退出的不算，没证明资源够）就回到按实测估。同队列一档的 OOM 不算（同一份清单里可以是完全不同的任务）。
  峰值是 10 秒一采的，几十秒就 OOM 的常常采不全，所以两头都取；放行时估计是 0、又在第一次采样前就 OOM 的，这次学不到。OOM 也可能是程序错误（batch 写大了）：不自动重排，照旧留 `.failed`，翻到整卡后再 OOM 一直挂着，由实验会话看日志。
  CPU（整数核 `cpus`，来源 `cpu_src`）另有顺序：清单的 `cpus=` 优先，其次同类近 5 次 1 分钟峰值核数（`cores_peak`，期 1 起才记，之前的旧行当没有历史）的最大值 × 1.1，都没有按 1 核（`CPU_DEFAULT`）。
  **`cpus=` 写多了按实测收小记账**（`cpu_shrink`，#91）：写了 `cpus=n`（n ≥ 2）的，同 tag › 同名第一档有峰值的近 5 次历史里至少 3 次（`CPU_SHRINK_N`），且每一次都是“给多了”（那次实际导出的核数——用量行的 `give`，即开跑时按那台配额封顶过的 `LABMON_CPUS`——不少于 n，1 分钟峰值不超过 n 的一半且少至少 1 核，同[`cpu_fit`](#cpu-与读写)的门槛），没开跑的按峰值最大值 × 1.1 取整记账，估计里另记 `cpus_set = n`，来源写成“清单 cpus=4 偏大：同 tag 近 3 次峰值 1.2 核 ×1.1（开跑仍给 4 核）”。只收记账：开跑导出的 `LABMON_CPUS` 与缺省线程数仍按 n（`cpu_threads`）；收小后跑的行给的仍是 n，峰值照旧低就一直收小；有一次峰值过了一半就回到按 n；在配额比 n 小的主机上跑的（导出的核数被配额封顶，峰值也被线程数封住）、把 `cpus=` 改大后的旧行、没记 `give` 的行（#99 之前）都不算数（#99）。`labmon worker status` 的运行、等待行末尾写“CPU 按实测记 N 核（清单 cpus=M…）”。
  取整（`job_cpus`）：四舍五入、至少 1，写 `cpus=0` 的是 0（不记账，CPU 再紧也不挡它）；平时约 1 核的任务 ×1.1 后仍记 1 核。
  显存要的是“估计值 + 1 GiB”（`need_mb`，准入、推演、放不下的判断与 `fit` 共用）。
  按历史估的超过一张卡腾空后能给的（总显存 − 给对方留的 − 1 GiB），放行时按整卡算（`card_need`）：卡上没有别的任务就放，原因里写“超过整卡按整卡算”。
  一次 OOM 的峰值就是整张卡，×1.1 之后比卡还大，不封顶的话同类任务永远排不上；配置没改的会再 OOM 一次、记失败。记账照估计值，跑着时这张卡不再放别的。清单里写的提示值超过卡照样“放不下”。
  内存同理（`ram_need`，#62）：按历史估的（含 OOM 后的下限）超过 labmon 全停时能给的减去余量，按这整份算，labmon 别的任务都没在跑就放，原因里写“估计 X GiB，封顶为 Y GiB”；
  不封顶的话翻倍后比容器还大的会一直“放不下”。记账照估计值，跑着时不再放别的；清单写的 `ram=` 超过容器照样“放不下”。

  请求同真放行（登记的 `--gpus` 限卡只在登记那台上算），判可以的按 `acct_job` 记进快照再判下一行；临时指令同真放行：持久的挡法、截止（续租、约定归还）前按这一行的预计时长跑不跑得完，
  借来的主机上对方的内存或 CPU 超出预留、刚回落时整台不开（同真放行的 `guest_block`，状态的 `guest.block`），只是某张卡超出的只不放那张（`room.owner`），给对方留的显存照 `room.keep` 扣进整卡封顶；时长同真放行按此刻同卡并行数（同 `k_now`）与在跑同类的进度估；独占看得到卡上 labmon 之外的进程（状态的 `gpu_procs`，停得了的保活不算）与整机认得准的外来核数（`room.other_cpu`）。fit 只多三条：

  卡近 10 分钟利用率低于 `UTIL_LOW`（50%）、上面在跑的近 10 分钟各 1 分钟窗口核数平均不少于给它的核数 × `CPU_BOUND_FRAC`（0.9）的（`cpu_fit` 的“给少了”，见[「CPU 与读写」](#cpu-与读写)：被 CPU 卡住），不在这张卡上开，说先给它那条车道加核（`cpus=`）、这台还能给几核；
  容器在限流时（状态的 `throttle`，门槛同 #39 的限流告警：`thr_step` 的 `THR_HOT`、`THR_COOL`）整台不开，说先减线程（`gpu_slack`，#37；同机多开车道的提示也用它）。
  放不下的结论：labmon 全停也放不下的（`nofit`：卡数、显存、内存、核数不够，原因与真放行同一句）写“这台跑不了”，其余写“排在已有车道后面”（#94）。

  卡近 10 分钟的利用率（状态的 `util10`，「在用时多高」：卡上有保活的那几轮不记；页面上用的是另一种口径「吃满程度」`gpu_busy`，见 [workbench.md「GPU 利用率」](workbench.md#gpu-利用率)）只列出来、不据此劝阻（#67）：nvidia-smi 的利用率是“有核函数在跑”的时间占比，到 100% 不等于算满，27 上的小任务并行 4 条与 6 条每条都是约 20 分钟。

  不用卡的写 `ram=`）：提示值常偏离实测，同卡并行时显存估小了会 OOM，内存估小了是容器 OOM；空卡上单跑与排在原车道后面单跑一样（#35 B 起；以前一律不开）。同一条清单里只有别的任务的历史时也这样（#61 以前按同队列判可以开车道）。

- **记账**：运行中的任务按 max(估计值, 实测) 记（显存、内存整个生命期都是；CPU 只在开跑后 10 分钟内，之后见下一条的回收），刚起来还没涨上去也按峰值占位；CPU 的估计封顶到记账上限（`cpu_give`，与 `LABMON_CPUS` 同一个数，推演里开跑的也这么记）。
  CPU 另有回收（#65）：开跑（接管旧 worker 的从接管起量）满 10 分钟（`CPU_WARM_S`）后，估计那一份换成近 10 分钟各 1 分钟窗口核数（`use.pks`）的最大值，不超过开跑时给的核数、不低于 1 核，再与此刻实测取大。
  估计取的是同类的 1 分钟峰值，多半出在开头的加载阶段；不回收的话之后整段按它占着（11-09 27 上两条估 2 核、只用 1 核的任务让约 2 核空着记账，要 2 核的等了半小时）。
  内存、显存是硬资源（超了 OOM），不回收；CPU 超用只是被限流变慢。推演里开跑的仍整段按估计记（偏保守），运行中的按快照里回收后的记账带进推演。labmon 之外的进程按实测记，旧 `gpu_queue.sh` 的任务不记账、按实测算在 labmon 之外（内存、CPU 都是）。占位任务不记 CPU。
- **放行**：选一张卡，空闲显存减去各任务还没占上的记账后够“估计值 + 1 GiB”；容器内存上限减去 labmon 之外收不回的内存（`anon` − 我们任务的实测；读数据留下的页缓存内核会先回收，不算别人的）与全部记账后，够“估计值 + 余量”（8 GiB 与上限 5% 取大）。
  收不回的内存 `anon` = cgroup 用量 − 文件页（`mem_unevictable`）：v1 是 `memory.usage_in_bytes − total_active_file − total_inactive_file`，v2 是 `memory.current − active_file − inactive_file`，
  含匿名页、shmem（`/dev/shm`、tmpfs、SysV 共享内存，没有 swap 时收不回）与记到 cgroup 的内核内存。不用 rss + shmem：3.10 内核的 v1（29）没有 `total_shmem`，只剩 rss 会把 `/dev/shm` 当成能回收的页缓存。没有 cgroup 上限时按 `/proc/meminfo` 的 `AnonPages + Shmem`；
  CPU 记账上限（配额向下取整，`cpu_cap`）减去 labmon 之外的（连着两轮超过 1 核才算，一轮尖峰与零碎的 shell 不算；借来的主机上取 max(对方实测, 预留)）与全部记账后，够这个任务的核数，不够写“CPU 不够”（卡在资源上，同内存）；同 tag 在跑的没到限额。
  读不到配额（没设 CPU 上限）时不记 CPU。不用卡的任务（`gpus=0`）同样要过 CPU 与内存。按历史估的核数超过 labmon 全停时能给的，按那整份算（`cpu_need`，同 `card_need`），原因里写“估计 N 核，封顶为 M 核”。
  记账可能超过可放的（实测比估计多、labmon 之外的变多、封顶放进来的任务开跑后按配额记，比全停时能给的多），这时要核的写“CPU 不够”，`cpus=0` 的照放。
  “CPU 不够”的括号里写核被谁记着：在跑几个、共记几核，其中几个还没回收（开跑不满 10 分钟、记的是估计）又记账比此刻实测多 0.5 核以上（与它们的实测；已回收的记的是近 10 分钟窗口核数的峰值，此刻低于它不算），labmon 之外（借来的主机上连同给对方的预留）占多少。
  把这几个多记的加回去就够的，代码是 `cpu_est`（句尾写“实际空着的够，是在跑的记账比实测多”），否则是 `cpu`（核真被我们自己的任务用着）。
- **内存闸门**：收不回的内存（`anon`，不算页缓存）超过上限 90% 时停止放行并记事件，不杀任务。
- **放不下**：labmon 的任务全停也放不下的请求（`ram=` 写的加余量超过容器内存，GPU 卡数或满足显存要求的卡数不足，或 `cpus=` 写的核数超过配额）等待原因写“放不下”；GPU 会区分主机卡数、清单选卡限制和单卡显存。每轮照样再试，但不算卡在资源上、不成屏障，免得整台主机所有项目都停住。
  `cpus=` 没超配额、只是 labmon 之外与给对方的预留此刻占着、全停也不够的，写“CPU 不够：…labmon 之外与给对方的预留此刻占 x 核…先等它们退下”（代码 `cpu_other`），同样不成屏障：留着它们也不会走。
- **CPU 被挡的告警**：`place` 给出原因代码（快照的 `code`），worker 记每个请求从何时起一直因 CPU 被挡、而且该告警（`CPU_ALERT_CODES`：记账比实测多挡住的 `cpu_est`、labmon 之外占着、要的比配额还多），满 10 分钟（`CPU_ALERT_S`）才在等待项写 `cpu_wait`（秒）；
  核真被我们自己的任务用着（`cpu`）是正常排队，不计时、不告警（#65 维护者定，同显存被挡）。
  换了原因、放行了就重新计时（要告警的几种之间换不算），worker 重启后也重新计时。等待事件把 CPU 的几种原因（`CPU_CODES`，含 `cpu`）算一类：可放核数随 labmon 之外的占用抖动、原因来回换时只记一条。看板只认这个字段告警（见 [workbench.md](workbench.md#告警)）。
- **排序**（`admit`，真放行与推演共用）：先看临时指令（被挡住的不参与排队、没有排位）。其余每一步从还没放的请求里挑一个（`fair_key`）：先比人，同一人（项目主人）的几个项目的 GPU 用量合起来算一份，小的先；同一人的项目之间 focus 的先（优先只在同一人的项目之间排前，不越过别人：维护者 2026-11-17 定，#23），再比用量 ÷ 权重，小的先；项目内先来先跑。放行一个（或成组的成员留下资源）就给它的项目先记上预计的卡·时，同一轮里这个人、这个项目后面的请求随之往后排。不抢占在跑的；独占任务不另排前面。
- **屏障与回填**：资源够的小请求可以越过在等的大请求；按上面的顺序第一个卡在资源上、等了 `wait_cap_min`（缺省 30 分钟）以上的请求成为屏障，排在它后面的只有预计在它放行前跑完的才放（回填，`fits_before`：现在 + 预计时长 × 1.2 不晚于屏障预计放行的时刻；这个时刻由推演只排它一个算出，`shadow`），其余写“让位”。独占任务留着的卡（主机）上同样可以回填。时长不知道的不回填；占位任务不受屏障限制。
  等了多久只算没被临时指令挡住的时间：挡住期间不算，解除后从那时重新起算（不然 pause 半小时一 resume，队首立刻满 30 分钟成屏障）；单元从申请时刻起算。看不到 GPU（nvidia-smi 没输出）不算卡在资源上、不成屏障。
- **公平份额**：用量是各项目在所有主机上的 GPU 卡·时，跑过的按半衰期（缺省 24 小时）衰减；在跑的与刚放行的，已跑的部分照样衰减，预计还要跑的整段都算上（开跑先记一笔）。
  卡数按占的份额（`card_share`）：独占整机算这台的全部卡，独占卡算卡数，否则 卡数 × min(1, 估计显存 ÷ 卡的显存)。跑过的读各主机的 `usage.jsonl`（只算记了 `project` 的行），别的主机在跑的读它们 `status.json` 的 `share.run`（按状态里写的 `t`，3 分钟内写的才算，每分钟重读；不看文件修改时间，共享盘服务器的时钟比各容器慢 3 分多钟）。
- **按人**（#23）：项目算在谁名下由看板定（`fleet.project_people`：项目主人的账号对应的组内人员；认不出人员的账号按账号自己算一人；没有主人的项目归管理员），随 `sched.json` 的 `owner` 发来（项目 → 人员名的短哈希，共享盘上不写名字）。权重只在同一人的项目之间起作用，人与人之间一人一份；`owner` 里没有的项目（看板上没有的、旧看板没写）合起来算一份，所以全都没写时顺序与按项目比一样。
- **调度设置**：主机清单的 `[sched]`（`half_life_h`、`wait_cap_min`、`[sched.weight]` 各项目权重，缺省 24、30、1；示例见 [examples/hosts.toml](../examples/hosts.toml)），看板写成各主机的 `sched.json`（另加上面的 `owner`），worker 每轮读；缺省值只在 worker。权重与优先也能在工作台总览的调度卡上改。
- **排位**：状态里等待中的任务带 `pos`（第几、轮到它时这人的用量合计 `puse`、优先没有、轮到它时项目的用量 ÷ 权重、是不是屏障、被哪个屏障挡着）与推演的预计开始 `start`；放行时记下等了多久（`wait`，分钟，运行中的状态与 `usage.jsonl` 都有），调度卡算平均等待。

## 预计时长

任务要跑多久由 worker 算（`duration`，分钟）：看板的预计时间（排队任务的推演、运行中任务没有进度时的退路）与截止前的准入、回填共用这一处；回填再乘 1.2（`DUR_MARGIN`），截止前的准入另有一个已含余量的时长（见下面[截止前按多久算](#截止前按多久算)）。依次看：

1. 同类任务（同项目、去掉种子编号的名字，如 `p1_sst2_bert_clean_s44` → `p1_sst2_bert_clean`）跑成功过的：这一个和记录都有估时就按同类 实际/估时 的中位数折算，否则取同类实际用时的中位数。
   记录里有估时与现在相同的，只用这些算比值：估时改过之后，按新估时跑完一次就以它为准。都不同、比值又不在 [1/3, 3]（`RATIO_OK`）里的，说明当时的估时写错了，
   取同类实际用时的中位数，来源写“同类近 3 次实际用时（当时估时与实际差 ×11.3，不按比值折算）”（#134：`est_min=3` 实际 28–53 分钟，改成 35 后以前按 ×11.33 估成 397 分钟，约定归还前一直不放）。
   估时改了 3 倍以上是因为任务真的变大时，这样会估小，跑完一次新的就纠正；
2. 同类还没有跑完的、有在跑的：在跑的同类按日志进度估的总时长（看板写来的 `eta.json` 里的预计结束 − 开始，开跑后写的才算；在跑的那一个自己不算）的中位数，来源写“同类在跑的 N 个按进度估”（#67：sm_vit 第一条跑着时已能估出约 300 分钟，同类排队的以前仍按清单的 90 分钟推演）；
3. 这一个写了 `est_min` 的，别的型号 GPU 上同类的 实际/估时（#139：借来的主机常是别的型号，同型号一条记录也没有，以前按清单估时，4 小时的约定前照放实际要 200 分钟的任务）。
   速度不同，只借比值、不用实际用时；口径同第 1 条（估时相同的优先，改过估时、旧比值又不可信的不用）。来源写“别的型号 A100 上同类近 5 次 实际/估时 ×3.33”；
4. 这一个写了 `est_min` 的，借别的名字的 实际/估时 折算（#113），依次看：同 `tag=` › 同名字前缀（第一个 `_` 或 `-` 及之前，如 `exp_`，与看板自动归组同一条）› 同一条清单 › 本项目；同型号的都没有，再按同样四档看别的型号的（来源前面写“别的型号 X 上”）。
   每一档取这一档最近 40 个跑成功、有估时的记录，按同卡并行数挑 20 个；实际/估时 在 [1/3, 3] 里的照借，偏得更多的只在离这一档的中位数不超过 3 倍、且这样偏的至少来自 2 个同类时才借（`borrowable`，#139）：
   项目一贯少估 3 倍以上时各类任务都这么偏，照借（以前一律不借，一贯 ×4 的项目新任务反而按清单估时）；#134 那种一次写错只在一个同类上（它跑了几次都偏 ×11），不借给别的名字。
   能借的至少 2 个才用这一档；比值取各条 实际/估时 的中位数（不按时长加权，几条要跑几小时的训练不主导）。
   来源写“同 tag proj-b 近 3 个 实际/估时 ×0.50”“同前缀 exp_ 近 5 个…”“同一清单近 4 个…”“本项目近 20 个…”。没写 `est_min` 的不借，照旧时长不明；
5. 清单的 `est_min`。

### 截止前按多久算

续租截止、约定归还前的准入（真放行的 `override_hit` 与推演里的截止同一个数）按 `duration` 给的 `cut`（已含余量，`with_cut`，#139）：

- 同类历史给的（第 1 条）：max(中间值 × 1.2, 同类挑出的那几次里最长的)；同类波动大时（5 次 50、55、60、80、90 分钟）按 90 算，以前按 72 算、5 次里 2 次超过；
- 在跑同类按进度估的：max(中位数 × 1.2, 其中最长的)；同型号借来的比值：× 1.2；
- 别的型号的记录、清单估时：× 1.5（`CUT_EST_MARGIN`，更没把握）。

回填（屏障、独占留卡、成组留资源）仍按预计时长 × 1.2。成组的成员取组里最长的 `cut`（别的主机上的成员读它 `gang.json` 的 `cut`）。
跑不完的等待原因写明怎么算的、估时从哪来：“约定归还 11-20 18:00 前跑不完（估 53 分钟 = 同类近 3 次里最长的（中间值 34）；同类近 3 次实际用时…）”“（估 72 分钟 = 60 × 余量 1.2；…）”（成组的写“成组 X 里最长的成员”），`labmon worker status`、`labmon status` 与看板等待表都是这一句；看到依据不对就改清单的 `est_min`（#134）。

只认跑完的（停下重排的只跑了一段）记录；同型号 GPU 的优先（没记型号的旧记录算同型号），别的型号的只借比值（第 3、4 条）。
同类与借来的比值的记录都按同卡并行数挑（`near`，#67）：用量行记着运行期间同卡平均几条 labmon 任务（`conc`，含自己，按时间加权，占位任务不算），
取与这个任务预计会遇到的并行数 k 最接近的那一档的最新几条：按比例比，`|conc − k| / k` 不超过最接近的那条再多 0.25（`NEAR_TOL`），单跑（1）与两条挤一张卡（2）分开（#138：以前按差“最接近的 + 1”，k=1、2、4 都取到挤着跑的 120 分钟）；同类那一支有一条对得上就用它，借比值的各档这一档不到 2 条时放宽到第 2 近的那条再多 0.25。不知道并行数的旧行（11-09 前、和别的任务同卡的）只在都不知道时才用。
k：写进状态的 `dur`（排队的行）与截止前的准入取此刻最空的那张卡上在跑的条数 + 1（准入在选卡前判截止）；状态里运行中那一行按它自己的 k（同 `run_end`，看板据它算剩余、写回 `eta.json`，#138）；推演按开跑时那几张卡上的条数 + 1 取（`Worker.dur_k`）；在跑的任务（看板还没写来预计结束时的 `run_end`、读写拥塞嫌疑）按它自己的：量到的 `conc`，还没量到时按此刻它那几张卡上的条数（`Worker.k_of`，#86）。`labmon worker fit` 的“同卡 N 条时约要多久”同样只认这台型号的记录、带上在跑同类按进度估的。
并行对时长的影响因类而异：27 上的小任务并行 4 条与 6 条每条都是约 20 分钟，29 上的 sm12 并行 8 条要 77 分钟、27 上并行 6 条 45 分钟；单跑的记录估不了挤着跑的。
占位任务就按 `est_min`，它的时长也不进借来的比值；写了依赖的占位任务开始即放行（见[依赖](#依赖)）。
worker 把各清单每个任务的预计时长写进 `status.json`（队列的 `dur`），探针带回看板；不归 worker 管的队列直接用 `est_min`。单元拿不到退出码，续租截止、约定归还前按单元自己的历史用时判断，没有历史时按 `--est-min`。
没有估时也没有同类记录的任务时长不明：排上后不知道何时结束，推演里它那条队列后面的、以及要等它腾资源的都不给预计开始。

## 推演

状态里的 `plan` 是推演（`simulate`、`forecast`）的结果：从现在起按 `admit` 与 `place` 同一套规则一轮轮放行，在跑的到预计结束时腾出资源、队列接着取下一个，排到 7 天。
只模拟显存（各卡按估计值记账，上限扣掉 labmon 之外的占用与给对方留的量；借来的主机上有对方另起、`ka.sh` 停不了的保活的卡不放，同真放行：它不会自己走，#45）、内存、CPU（labmon 之外的按此刻当常量）、独占（留卡与回填）、tag 上限、截止前的准入与公平份额；缺本地文件、内存闸门、对方超出预留这类等不来的原因不模拟，共享盘慢时的让路与读写拥塞嫌疑是此刻的信号，也不模拟。被持久的临时指令挡住的队列（暂停、drain、截止前跑不完、借来的主机只给别的项目用）不推演；借来的主机上对方此刻超出预留的照常推演（真放行照旧挡住，此刻才有的原因推演不模拟；`override_hit` 的 `lasting`，#25）。

- 运行中任务的预计结束取看板按进度算的（`eta.json`，任务开始之后写的才用；占位任务不用，它没有进度），没有就按预计时长（`run_end`）；超过预计的，剩余按已跑时长的 20% 估、至少 10 分钟，不当“马上结束”。
- 写了依赖的任务排在依赖都满足的时刻；写了依赖的占位任务结束取 `dep_end`（依赖都满足的时刻），推演、运行中的预计结束与看板都用这一个值（见[依赖](#依赖)）。
- 结果：`{"t", "lanes": [{root, queue, project, kind, jobs: [{name, t0, t1, gpus, run?, after?, deps?}], stuck, stuck_dep}]}`。`after` 是要等谁腾出资源才轮到（`[[项目, 任务]]`），
  `deps` 是它写的依赖（`[[项目, 任务]]`，`afterany=` 的第三项为 `"any"`；看板写“等 X、Y 跑完”、画依赖连线）；排不上的写 `stuck`（放不下、截止前跑不完、等的任务跑不成或不知道何时跑完、前面的占位任务不知道何时放行、前面的某任务不知道要跑多久、等某任务腾资源而它不知道要跑多久、推演 7 天还没轮到）；
  其中停在依赖上的（等的任务跑不成或不知道何时跑完、前面的占位任务不知道何时放行）另在 `stuck_dep` 写停在哪一行，别的原因与排得上的为 null（offers 据此分“原处跑不了”与“不知道”，#183）。
- 等待中的、运行中的任务、临时指令或 eta 变了就重推，否则 2 分钟一次。

### 能接别处的任务（offers）

推演完 worker 还算一遍：同一项目在别的在用主机上排得很晚、这台又将空着时，这台能接过来哪几行、接来后几点跑完（Issue #20）。
结果写进状态的 `offers`，看板据它出挪法建议（[工作台「挪法建议」](workbench.md#挪法建议)）；labmon 不改清单、不改放行，挪不挪由实验会话定。

- 来源：`peers` 读到的别的主机状态（过期的、`worker stop` 过的（含借用归还）不读）：还会跑的行取它的 `todo`（见[依赖](#依赖)，与依赖同一份），预计时刻取它的 `plan`，
  各行的资源提示从清单文件取（按修改时间缓存，同名的行取第一条：worker 跑的是第一条）；暂停的清单、项目在那台暂停的不算（主机 drain 又暂停了本项目时 `todo` 写 pause）。
  - 在原处跑不了的照样能挪（续租截止挡住的也算，维护者 2026-11-08 定）：推演里排不上（`plan` 写了 `stuck`：放不下、时长不明、截止前跑不完…），或被持久的临时指令挡住
    （约定归还、续租截止、drain、只给别的项目用；那台等待项的 `held`）。借来的主机上对方此刻超出预留的清单照常推演（见[推演](#推演)），队首快开跑时同样不挪。
  - 推演停在依赖上的（`plan` 的 `stuck_dep`：等的任务跑不成或那台说不出何时跑完、前面的占位任务不知道何时放行）不算在原处跑不了：挪走的行带着同样的 `after=`，
    原处只是此刻说不出依赖何时满足（两台的 `after=` 交错成链时，一台一轮没算出的依赖时刻会沿着链来回传几轮），按下一条“不知道”处理（#183）。
  - 推演里没有、又说不出为什么的（读不了状态目录、队列没出请求），以及 worker 不在的主机（状态过了 3 分钟、没 `worker stop`、一天以内：续租、重启）上的清单（看板写来的 `returned.json` 里的主机除外：自用主机 `host return` 或平台上关了机都标成已归还，它们不挡；依赖照旧把它们的 `todo` 当还会跑，维护者 2026-11-09 定）：
    不知道原处何时放行、何时跑完，这个项目一行也不挑（这台空着时只跳过这条，见下面的 `idle`），整批推不出（`ends` 里是 null）。来源主机读不到清单文件时那条清单整条不在 `todo` 里，
    整批完工会估得偏早：这只在 NFS 读失败的那一两轮出现，不另处理。
- 挑哪几行：取这个项目此刻排得最晚的那条清单的队尾一行（只从尾巴取：清单里没写 `after=` 的先后 labmon 看不出来），那条清单的完工随之提前，
  再取此刻最晚的，至多 20 行（`MOVE_MAX`）；最晚的已不晚于本机这个项目何时跑完就停。逐行加进推演时，挪来的前几行已不早于原处剩下的最晚完成时间就不再往下试
  （`moved_past`：再挪只会更晚，整批与下面按行比都不会更好；原处有说不出何时跑完的清单时不判）。以前在原处跑得了的只挑 5 行：行短、晚得多时（同卡只放得下两条、
  第三条车道排在别的车道后面才跑完，#110）挪满 5 行也不到门槛，一直不建议。
  队尾是占位任务、原处 10 分钟内就开跑（`MOVE_LEAD_S`）、有别处的任务写了 `after=` 等着它（挪走后它何时开始会变；别处含 worker 不在、已归还的主机与算力池里待放的，`peer_todo`）、`needs=` 缺了在这台又补不了、
  清单文件里找不到（刚剪过）或读不到清单、与前面挑的不是同一种环境（目录与 `.env`：任务在清单的目录下跑、读这条清单的 `.env`）的到此为止，原因写进 `why`。
  - 这台空着（`Worker.idle`：没有 labmon 任务在跑，占位任务不算；这一次的推演里也没有 10 分钟内就开跑的）时 `idle` 为真（#62）：上面停的原因只跳过那一条清单、
    接着看别的清单，说不出原处何时放行的清单（停在依赖上、推演里没有、那台 worker 不在）也只跳过它；`why` 记第一条跳过的原因。看板没有整批的挪法时按行比（[工作台「挪法建议」](workbench.md#挪法建议)）。
- 几点跑完：把前 k 行加进这台的推演，走同一份 `simulate`（本机别的项目、公平份额、约定截止、依赖、独占都照真推演），挪来后排不上的到此为止并写原因。
  写了 `after=` 的行按 `dep_state` 同一口径判（别的主机的 `todo` 与 `plan`、各主机的用量记录）：别的主机上有行写了依赖时，本机没有依赖也照算。
  挪来的行按在车道里的位置认（接在原有的行后面），不按名字：同项目几条清单可能有同名的行。接在的那条清单里有写了 `after=`/`afterany=` 的行时，
  挪来的插在第一条这样的行前面（`before`：清单顺序也算依赖，接在它后面会被它堵住）；挪来的几行里写了依赖的排在独立行后面（#43）。
  挪来的那一行没有估时、推演里排不上时 `nodur` 为真，看板据此出 `rebalance:<项目>:est`。
  这台已有这个项目、目录与 `.env` 都和挪来的行一样的清单（`.env` 里 `QUEUE_STATE`、`QUEUE_LOGS` 两行是各条队列自己的状态与日志目录，不比；空行不比，剩下为空的与没有 `.env` 算同一种）就接在预计最早跑完的那条后面（不建议同机多开车道），没有就当新的一条。真把这几行挪过来，推演给的结束与 offers 里的一样。
- 同机挪到另一条早跑完的清单（#110，`lane_offer`）：本机这个项目排得最晚的清单（常见的是同卡只放得下几条、它排在别的车道后面才跑完，卡在最后空着一半），
  队尾几行接到本机目录与 `.env` 都一样、预计最早跑完的另一条清单后面（那条里有写了 `after=` 的行就插在它前面，同跨主机的 `before`），
  同一套挑法（`move_cands`）、推演（`try_move` 从原队列拿掉、接进那条清单）与门槛。车道数不变、同时跑的条数不变，所以不看卡的余量、只有提示值的 GPU 行照挪。
  每项带 `local: true`、`lane` 是接在后面的那条 `[目录, 清单]`，`jobs` 的 `rest` 是新推演里原清单何时跑完；挪不了的不列。
- 同机多开一条车道（#43，`local_offers`）：本机这个项目排得最晚的清单的队尾几行，同一套挑法（`move_cands`）与推演（`try_move` 从原队列拿掉这几行、
  原样放进一条新车道），每项带 `local: true`、`lane` 为 null，`jobs` 的 `rest` 是挪完后本机原清单何时跑完（新推演里，同卡变慢也算进去）。只在卡有真余量时算
  （`local_cards`，与 fit 同一条规则 `gpu_slack`）：容器在限流、各卡近 10 分钟利用率都不低于 `UTIL_FULL`（90%）、利用率低于 50% 的卡上在跑的被 CPU 卡住的都不出，
  新车道只许用余下的卡（不是全部卡时记在 `gpus`，建议的 `worker add` 带 `--gpus`）；估计只有清单提示值的 GPU 行不挪（同卡并行怕 OOM）。同机不出的不写原因（`fit` 会说）。
  原推演里本机这个项目何时跑完推不出时算不了收益，只在要挪的行没有估时那样留一项 `nodur`（`jobs` 为空），看板据此出 `rebalance:<项目>:est`。
- 这台还能多开几条（#145，`lane_room`）：跨主机的与同机多开车道的每项另带 `room {busy, lanes}`，只在卡有真余量（`local_cards`，同上）、候选第一行要 GPU 时给，否则为 null。
  `busy` 是能放的那几张卡近 30 分钟（`UNDER_WIN_S`）「吃满程度」的平均（只有保活的那几轮记 0，同状态的 `gpu_busy`；worker 起来不满 30 分钟为 null）；
  `lanes` 按候选第一行的资源形状在此刻的快照上逐条 `place`、记进快照再判下一条（同 `fit` 假设开车道的做法），至多 32 条（`ROOM_MAX`）、不超过来源还会跑的行数。
  只看此刻的资源、不扣别的项目在等的请求；看板据此判这台吃不满（[工作台「挪法建议」](workbench.md#挪法建议)），会话照做前用 `fit --list` 核对。
- 这个项目在这台不能用（drain、只给别的项目用、暂停）或这台在预备续租（续租截止）的只写原因，不接；借来的主机上对方此刻超出预留不算（几小时后接不接得了，推演不模拟它）。
- 只是提示：算 offers 出错时沿用上一次的（最多 3 分钟，`STATUS_STALE_S`，再错就清空）、worker.log 记一行（同一个错只记一次），放行与推演照常。
- 字段：`[{project, local, gpus, lane, before, free, ends, jobs: [{host, root, queue, name, there, rest, end, own, dep}], why, stop, nodur, idle, room}]`（`local`：同机的挪法，`lane` 为 null 是多开一条车道，否则是挪到本机那条清单；`dep`：这一行写了依赖；`idle`：这台空着，同机那两种不带）：`why` 只放原因本身，`stop` 是挪到这台排不上的那一行
  （与具体某行无关的为 null），原因句由看板拼；见 [schema.md「工作台的全局快照与接口」](schema.md#工作台的全局快照与接口)。

## 保活

有 GPU 任务在跑、或有会放行的 GPU 请求时停保活，并在 `$AGRI_ROOT/queues/labmon-<主机>/pid` 登记；被临时指令挡住的请求（暂停的项目、drain、续租截止、只给别人用）、依赖没满足的和等不来的请求（放不下、缺本地文件又补不了、tag 到上限）不算，卡空着时保活照开。
`ka.sh` 是随 worker 发来的那份（`worker_home/ka.sh`，认法、退出码与日志见 [fleet.md「ka.sh」](fleet.md#kash)），配置读 `ka_bin` 里的 `ka.env`，两样缺一样 worker 就不管这台的保活。
都没有时删除登记，每约 30 秒看一次：连续两次本机没有别的队列登记存活、GPU 上也没有任何进程，才 `ka.sh start`；
保活在跑时 GPU 上有了别的进程（借来的主机上多半是对方回来用）就 `ka.sh stop` 让路，同保活守护。
平台的保活按整台算（见 [fleet.md「保活守护」](fleet.md#保活守护)），多卡主机也只开停这一个。

要卡的这段里保活停过又被拉起来，worker 下一轮照样停掉；不是旧 `gpu_queue.sh` 退出时拉的（看门狗、别人的脚本），再记一条“保活被拉起”事件：
写明 ka.sh 记的调用者和找到的看门狗。调用者取 `$AGRI_ROOT/keepalive/events.log` 里这台的那条 `RESTORED`：这份日志在共享盘上，各容器的 ka.sh 都写、行里不带主机，
所以只认进程组是此刻在跑的保活的（`ka.sh running` 打印的）、时刻（带时区）在停保活之后、又在保活进程启动后 30 秒内的（ka.sh 起来后最多等 20 秒才记；不同容器的 PID 常撞号）；
没有对得上的写“不是经 ka.sh 拉起的”（#123）。
状态的 `kafight`（近 1 小时被拉起几次、最近一次、是谁）让工作台这台主机出告警，1 小时没再被拉起就消失。

**自己开的保活**（#102）：空闲时经 `ka.sh start` 拉起、`ka.sh running` 只列出一个进程组、事件日志里它的 `RESTORED` 是这台 worker 记的（同 `ka_caller` 的认法），
就记下它的进程组与组长出生时钟（状态的 `keepalive.mine`，重启接管找回）；它没了（被停、被人 `pkill`、换了容器）就清掉，不记事件。借来的主机归还时据此把它登记成看板的保活（[fleet.md「借用」](fleet.md#借用)）。

**停不下来**（#102）：要卡时 `ka.sh stop` 没停成（退出码非 0，原因取它标准错误的末行），或 `ka.sh running` 说没在跑、GPU 上却有它管的保活（`ka_owned`），都算一次没停成。
连着没停成满 2 分钟（`KA_STUCK_S`）且至少两次，算 worker 停不了它：记一条“保活停不下”事件（`ka_stuck`：哪个保活、占多少、原因，借来的主机写“请对方停掉它或查 ka.sh”），
状态的 `keepalive.stuck` 让 `labmon worker status` 不再写“有任务要卡时 worker 自动停”，改写“worker 要卡时停它没停成（原因，几点起几次）”，工作台这台主机出给用户的告警。
这时照放这张卡：真放行本来就按 nvidia-smi 的实测空闲放（保活占的已扣），推演把它的显存算进卡上 labmon 之外的占用，`fit` 不再把它加回空闲，三者都当它一直占着。
worker 照旧每轮再停，停下了（或保活自己没了）当轮清掉、只写 worker.log；任务之间的空档不清，同一段只记一次事件，worker 重启接管时从上一份状态找回。
借来的主机上对方另起、`ka.sh` 认不出的保活（下文「借来的主机上」）是另一回事：那张卡不放。
worker 重启（部署的 `--replace`、`labmon worker start`、续租后拉起）不清零：新 worker 从上一份状态找回各次的时刻（`kafight.hits`），告警照样撑满 1 小时；
上一份状态 3 分钟内（`STATUS_STALE_S`）写的、当时停着保活（`ka_stop`），接管后第一轮见到保活在跑也记“保活被拉起”（重启那段里被拉起的），停得更久的不沿用（#124）。
同卡上保活那段记在任务用量行的 `with_gpu` 里，在跑的独占任务另在队列日志里记一笔。保活一般当轮就停，运行中的独占任务只计到一轮、不作废；停不下来的（自用主机上看门狗每轮拉回）连着两轮照样作废，借来的主机上推迟暂停看门狗的例外见下文「暂停前先看锁」。

**看门狗**（`watchdogs`）只看 shell 与 python 跑的脚本（交互 shell、二进制程序不算），跳过 labmon 自己的（worker、任务、`ka.sh`、`fleet_guard.sh` 与它在后台盯着的那个、旧 `gpu_queue.sh`）和用着 GPU 的。
“提到保活程序”指脚本里有 `train_keep_alive.py`、`keepalive_guard.sh`、`ka.sh` 这类文件名，连同它直接调到的脚本一起看（循环脚本常去调另一个拉起保活的脚本）；脚本文件已删掉的，从 bash 还开着的 fd 255 读。

- 确定的：保活的父进程（前台起保活、等着它的脚本）；保活的上级进程或同一会话里提到保活程序的；提到保活程序又在循环里的。
- 可能的：只提到保活程序、没见循环的；保活更上级的进程；循环盯着 GPU 的；提到保活程序的 1 号进程；cron 在跑时定时任务里提到保活程序的；
  够得上确定、但下面在跑程序的（python 或用着 GPU 的：对方的实验队列跑完一批再拉保活，暂停它会耽误对方后面的实验）。
- 1 号进程不算保活的上级：`ka.sh` 拉起的保活脱离后父进程就成了它（平台容器的 1 号是 `sh -c "… && sleep infinity"`）。

借来的主机上，一借来（第一轮）就找一遍，之后每 10 分钟、保活被拉起时也找。找到的一律当出借方的进程，不按路径猜归属：
调了 `/root/data1/alice/…` 下的保活工具、注释里写着 alice 都不说明是自己的（保活工具是 alice 部署给全组用的）。
平时只列出来（`hosts/<主机>/frozen.json` 的 `seen`），不预先暂停：组里的 `ka-watchdog.sh` 认 labmon 的登记，不会来拉。
要卡时保活真被拉起来了，才 SIGSTOP 暂停当时找到的确定的，记进 `frozen.json` 的 `frozen`；它被恢复后又拉起来，再停一次。代价是第一次被拉起时保活多跑一轮。
新找到的各记一次“看门狗”事件，组内服务器抽屉的借用一节也列着，`labmon worker status` 同样打印。

**命令行里的保活**（#61）：`labmon worker status <主机>` 与 `labmon status` 的主机行下各写一句这台的保活：在跑的写几点起、nvidia-smi 里的 PID（宿主机的；容器内 PID 不同时括号里另写）、在哪几张卡、占多少显存，以及有任务要卡时 worker 会自动停（停不下来的改写没停成的原因与次数，见上文「停不下来」）；停着的写 worker 何时为要卡的任务停的；没在跑的写不拉起的原因或等卡连着空两轮后拉起；借来的主机上 ka.sh 停不了的保活另起一句（那几张卡不放）；近 1 小时被拉起过的写次数与是谁。归属照 `sample` 认的（`gpu_owners`、`ka_owned`），命令行不另判。

**命令行里的 CPU 配额**（#112）：`labmon worker status <主机>`、`labmon worker fit`（`--list` 每台的开头）与 `labmon status` 的主机行下各写一句这台的 CPU（`cpu_line`）：容器配额（不是整数的另写按几核记账）、`nproc` 报的是宿主机的核数、labmon 在跑几个任务记了几核、labmon 之外（借来的主机上含给对方的预留）占几核、还能给新任务几核（状态的 `room.cpu`）；没设配额的写不按核记账。`worker status` 的运行行另写这个任务记几核（状态 `running[].acct.cpu`）。

**出借方自己的保活管理器**（#31，以 BOB 的 `keepalive_control.py` 为例）：guardian 起 watchdog，watchdog 每 5 秒按登记文件（`keeper_identity.json`）看 keeper，不在、又没有它登记的实验就拉起；
keeper 用 `start_new_session` 起，只做 setsid、不改父进程：由 `run`、`start` 这类会退出的命令起的，命令退出后父进程是 1 号；watchdog 自己拉回的是 watchdog 的子进程，
watchdog 因此按“拉起了保活（PID … 的父进程）”认成确定的。保活连同它的整棵子树（DataLoader 等子进程，spawn 起的命令行不带 `keep_alive` 也算）不算看门狗“下面在跑的程序”。它的 keeper 与 `ka.sh` 是同一个解释器、同一个脚本（组里 `server.env` 的 `AGRI_KA_*`），所以：
- worker 认得它（`gpu_owners` 给 `owner: keepalive`），要卡时 `ka.sh stop` 停的就是它；不必按登记文件认看门狗，watchdog 的脚本里提到保活程序又在循环里，按内容就是确定的，guardian 下面在跑 watchdog，归可能的、不动。
- 不会两个保活并存：对方的在跑时 `ka.sh start` 见已在跑就不起；labmon 起的在跑时，对方的 `start_keeper` 按同样的命令行认到它、不是自己登记的，先停掉再起自己的。脚本不同的出借方保活走下面一段（停不了，那张卡不放）。
- 第一次停保活后 watchdog 拉回，worker 下一轮见“保活被拉起”就暂停它，之后不再拉锯；还卡时 `thaw` 恢复。它醒来见到不是自己登记的保活，换成自己的，结果仍是一个保活在跑。
- 不调用对方的让路接口（`keepalive_control.py run -- 命令`：停 keeper、整个命令期间持着它的锁、在对方目录里登记、命令退出后拉起 keeper）：持锁期间对方自己的 `run`、`start` 都起不来，比暂停 watchdog 更碍事；
  而且要执行对方的程序、写对方的目录，超出 AGENTS.md 借用的例外（2026-11-08 维护者定，#31）。暂停 watchdog 一般不挡对方自己的 `run`：它只看 watchdog 进程在不在，暂停的进程还在，锁也空着。
  例外是 watchdog 拉起 keeper 的那几秒：它在 `exclusive()` 里持着同一把锁，等 keeper 起稳约 8 秒。暂停若落在这段里，锁就随暂停一直占到还卡（#38）。
  所以暂停前先看它持着的锁（见下一段）。

**暂停前先看锁**（#38）：worker 读 `/proc/locks`（`held_locks`），取确定的看门狗此刻持着的文件锁：FLOCK、POSIX 锁按持有者 PID 认，OFD 锁按它开着的文件认。
每次找看门狗时（借来第一轮、之后每 10 分钟）给确定的记下它平时持的锁（`frozen.json` 里 `seen` 的 `locks`），同一进程每次与上次取交集，只出现过一次的筛掉。
BOB 的 watchdog 一生持着自己的单例锁，所以不能“持锁就不暂停”，要看比平时多出来的。已暂停的不再看：停着拿不了新锁，之后保活再被拉起时对它只是再发一次 SIGSTOP。
保活被拉起时，确定的看门狗里有一个持着平时不持的锁，或还没记过它平时的锁（上次找过之后才出现），这一轮就一个都不暂停，也不停保活：
停了它会再拉一次、又持锁。worker.log 记一行，下一轮再看；锁放了再暂停、停保活，“保活被拉起”事件只记一次，写明推迟了多久。
要卡这段里第一次记的那份（保活被拉起时才看到的，或保活已被 worker 停着时找到的）可能正落在它拉回保活、持锁的时候（约六成），交集筛不掉：
所以这一份另记 `locks_t`，要等它比这份少了一把（放了锁）再暂停；一直不少（多半这份就是平时的），满 1 分钟（`LOCK_WAIT_S`）到点暂停。
此刻一把锁都不持的看门狗不用等，有没有基线都直接暂停。
一直持着平时不持的锁满 1 分钟也不暂停，记一条“看门狗”事件：保活停不下来、和任务同卡。所以代价一般是保活与任务同卡多一轮（约 10 秒），带 `locks_t` 的最多多 1 分钟。
推迟中保活自己没了（多半是同卡显存不够、CUDA OOM），推迟到此为止，这次被拉起照样记一次“保活被拉起”，看门狗不暂停。
运行中的独占任务在推迟的这段里（不到 1 分钟）不把保活算打扰（`void_check`），一般只多一两轮；满 1 分钟还停不下来的照旧连着两轮作废。
同卡的任务若在这段里 CUDA OOM，按失败记（`squeezed_by` 只认对方的进程，保活不算），不按被挤掉重排。
读不到 `/proc/locks` 时照旧暂停。认不出的情况，照旧会暂停在锁里或多推迟：
- 锁是看门狗一直持着、只在 keeper 死后才放的那种设计：基线里就有它。
- 第一次记基线时它正好持着锁，还有两条路径会发生：worker 重启后的第一轮（这时还不知道保活是不是自己停的，找看门狗又先于停保活，记的第一份不带 `locks_t`）；
  带 `locks_t` 的那份，它从被看到起持锁满 1 分钟，到点照样暂停在锁里。两种概率都小，也不比不看锁差。
- bash 看门狗常见的 `exec 9>lock; flock 9`：锁是 `flock(1)` 子进程加的，`/proc/locks` 记的是那个已经退出的 PID（新内核在容器里干脆不列这一行），认不到看门狗头上，照旧可能暂停在锁里。
- OFD 锁按“它开着这个文件”认：别的进程对它也开着的文件加了 OFD 锁，也算到它头上，结果是多推迟（满 1 分钟记事件，不暂停）。

锁文件若在共享盘上，NFS 缺省把 `flock` 发给共享盘服务器，别的容器里用同一目录的也会被挡，这也是不能暂停在锁里的原因。

借来的主机上，`ka.sh` 认不出的保活 worker 停不了（GPU 进程 `owner` 为 `other`、`ka` 为真）。ka.sh 认的（`ka_owned`，与 ka.sh 的 `ka_procs` 同一条，#29、#105）：
python 跑 `ka.env` 的 `AGRI_KA_DIR/AGRI_KA_SCRIPT`，命令行里写着这个完整路径，或跑的脚本相对路径按进程工作目录（`/proc/<pid>/cwd`）还原、解开符号链接后就是它
（先 `cd` 进保活目录、用 `train_keep_alive.py`、`./train_keep_alive.py` 起的也算；别的目录里的同名脚本、`python -c`、工作目录读不到的不算）。停不了的保活：
那张卡算超出预留、不放新任务（推演里同样不放：快照里这张卡的 `ka` 为真，`sim_snapshot` 照它挡；等待原因写“卡 N 上有对方另起、ka.sh 停不了的保活，不放（要停请对方停）”，推演排不上时写“显存不够（卡 N 有停不了的保活）”，#45），事件里写明要对方停；它整棵进程树的内存与核数不算对方的用量，核数另从可用核数里扣（见上文「借来的主机给对方留余量」）。借来时就有这种保活的本来就借不了（`borrow.begin` 逐个核对，要对方先停，见 [fleet.md「借用」](fleet.md#借用)）。
还卡时 `borrow.finish` 开完保活再跑 `labmon_worker.py thaw` 恢复它们：核对 PID 与启动时刻，PID 已被复用的不碰。自用主机上只记事件，不暂停。

## 单元申请

自带监督进程的项目（如 示例项目）不用清单，每个单元启动前申请：单元命令前加前缀，阻塞到放行后设好 `CUDA_VISIBLE_DEVICES` 再 `exec` 原命令（进程号与退出码不变；进程一退出名额就收回）：

```bash
python3 /root/data1/alice/labmon/labmon_worker.py slot --host 29 --project demo-b --name <单元名> --ram 30 --vram 4 [--gpus 1] [--tag heavy] [--exclusive gpu] [--cpus N] [--io heavy|light] [--est-min 分钟] [--stop term] [--log 路径] [--timeout 秒] -- <原命令…>
```

- 申请经容器本地 `/tmp/labmon/slots/` 的小文件交换（不走 NFS，没有时钟偏差），worker 约 2 秒内处理；等待期间每分钟往 stderr 写一行在等什么；worker 不在时一直等（`--timeout` 到了退出码 75）。
- 监督进程登记成清单任务时，它起的单元的内存、CPU 只记在单元上，不重复记；监督进程自己不用卡、几乎不占 CPU 时，整机独占不等它，也不算打扰。
- 监督进程自己的内存闸门、选卡、重型任务锁与保活租约都改由 labmon 管，单元列表、依赖、续跑与回执不动。

## 临时指令

项目的暂停、优先缺省是所有主机的（含之后新开、借来、换了 id 的，#96）：记在主机清单的 `[sched.pause]`、`[sched.focus]`（一个项目一行，值是到期时刻或 `true` 无期限；暂停是谁下的另记在 `[sched.pause_by]`，看板自己写、worker 不读，#16），
看板每轮随 `sched.json` 写给各在用主机，worker 当成同名的临时指令（`sched_ovr`），约 1 分钟内生效；看板没开时 worker 用上次写的那份，到期照样不挡。
带 `--host` 的、drain 与看板下的截止存在各主机的 `hosts/<主机>/overrides.json`，只管那一台；经看板下的带 `--host` 的暂停、优先另记谁下的（条目的 `by`，看板的账号名，#27）。都带到期时间，工作台列出：

```bash
labmon pause demo-b [--until 11-10] [--now]   # 不再放行它的新请求；--now 再按各自的停法停下正在跑的（停法以现在的登记为准，重新登记 --stop term 对正在跑的也生效）
labmon resume demo-b                          # 撤所有主机的暂停（--host 单独下的要带 --host 撤）；普通用户只能撤、改自己下的，管理员（或没记是谁）下的找管理员，带不带 --host 一样（#16、#27）
labmon focus a1 --until 11-17              # 它的请求排在同一人别的项目前面（不越过别人的项目，仍受余量限制）；只给管理员（#16）；总览的调度卡上也能点「优先」「暂停」
labmon unfocus a1
labmon drain 29 [--until …]               # 这台主机不再放行新请求
labmon undrain 29
```

- `--until` 写 `11-10`（当天结束）、`11-10 18:30`、`2026-11-10[ 18:30]`、`明天 9:00`（今天、后天同理）、`21:45`（今天）、`+30m`、`+3h`、`+2d`，精确到分；不写年份的按今年，早于现在半年以上的才算明年（12 月底写 `01-05`），已经过去的拒绝。`--host` 只对某台主机（缺省所有主机）。
- 不带 `--host` 的 `pause --now`：写所有主机的暂停，另给各在用主机下一条“只停一次”（`once`），worker 按停法停下这个项目正在跑的，之后它照样当暂停挡着，等全局暂停随 `sched.json` 送到才删（最多挡 30 分钟，`ONCE_HOLD_S`），所以 `resume` 一条就撤干净。
- 另有两种由看板下、用户不直接写的：`deadline`（截止前跑不完的不放行）——续租截止由预备续租自动下、取消预备时撤，目标 `borrow` 的是借用的约定归还，没估时的任务到点前照常放行；`guest`（借来的主机，见上）。借用还了就撤。
- 停法在登记时声明（`worker add --stop`）：`boundary`（缺省，等当前任务跑完）、`term`（SIGTERM，项目自己续跑）、`file:<相对 ROOT 的路径>`（写项目约定的停止请求文件）；被暂停停下的任务重新排队，不记失败。
  `file:` 的路径必须在 ROOT 内，不能含 `..`，符号链接解析后也必须留在 ROOT 内。新登记校验不通过时保留原登记。
  旧登记触发越界时，worker 记录失败，正在跑的任务继续运行。用合法停法重新登记后，新开的任务按更新后的停法处理。
- 最常用的“把服务器让给别的项目”就是 `pause`：正在跑的自然跑完，急的加 `--now`。

## 事件

开始、放行、完成、结束（单元）、失败、中断、暂停、闸门开关、内存撞上限次数增加、临时指令、等待原因（类别变了才记，原因里的数字不算）、拷本地依赖与写回主副本、作废、被挤掉、对方超出预留、队列跑完、worker 启动写进 `hosts/<主机>/events.jsonl`。
临时指令事件带 `act`（add / rm / expire）、`okind`、`target`、`until`，项目页时间线按它画区间。worker 启动时文件超过 4000 行才截到最后 2000 行；看板把除任务起止之外的事件续存进本机 `hostlog/<主机>.jsonl`（30 天），项目页经 `/p/<id>/events.json` 取，工作台的记录页也读它。

## 接管与重启

- worker 被停或升级时任务照跑，新 worker 启动后接管并照常记完成（已放行的单元也接着盯）。升级（`worker start` 已在跑时，`--replace`）是让旧 worker 在它这一轮 tick 结束时退出，新 worker 一直等它退了才接管，任何时候只有一个在放行；拷本地依赖、扫共享盘与本地盘这类慢 IO 在后台线程做，不拖住调度。
- 服务器重启就是容器重启：任务与 worker 都没了，容器盘重置。主机清单标了 `worker = "auto"` 的主机由看板自动拉起（见 [workbench.md](workbench.md#工作台数据与自动拉起)），否则手动 `labmon worker start`；中断的任务从头重跑（`queue.log` 记“中断”），任务内部的断点续跑由各实验自己负责。容器重启后 PID 会被复用，worker 按任务名核对进程，不会认错。
- 监督进程本身也随容器消失：项目的续跑命令可以直接重跑时，把监督进程登记成一条 `gpus=0` 的清单任务，容器重启后由 worker 自动续跑。
- 与旧 `gpu_queue.sh` 共存：某条队列的 `lock` 指向存活的 `gpu_queue.sh` 时，worker 不碰这条队列，只在状态里写明在等它。

## 共享盘

- **目录规范**：`labmon project init 29 [项目]` 在主机的 `data_root` 下建规范目录，写入说明 `README.md`（原文是 [`labmon/data_root_readme.md`](../labmon/data_root_readme.md)），并列出现有的共享环境、数据集与权重：`projects/<项目>/` 放各项目自己的东西，`envs/`、`datasets/`、`weights/` 放各项目共用、只读引用的环境（按版本命名，建好不改）、数据集和权重，`archive/<日期>/` 放压缩归档与删除清单，`labmon/` 放 worker。
- **用量统计**：主机清单写了 `shared` 的自用主机，`labmon worker start` 把第一个目录交给 worker（`--shared`）限速轮流扫（`Disk`），只有一台在扫；借来的主机不扫。登记了清单的项目根（各台状态的 `storage.projects`，扫描那台把别的主机的也合进来）拆开扫，项目根下的一级目录各成一个单位；各主机上有清单任务跑完（成败都算），扫描那台按用量行把它的项目目录提前重扫（`Worker.disk_ends`，#53）。怎么扫、怎么归人见 [fleet.md「共享盘」](fleet.md#共享盘)。
